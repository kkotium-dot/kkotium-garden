## 배경 — 실측 확정 사실 (추측 금지, 전부 grep+DB 확인됨)

1. `Product.substituteInfo`(Json?, schema.prisma L205)는 **단일 객체** 구조.
   실제 DB 값 예시:
   ```json
   {"hasSubstitute":true,"substituteName":"...","substituteNote":"...",
    "sourcingUrl":"...","sourcingCode":"...","lowStockThreshold":10,
    "substituteProductId":null}
   ```
   대체상품 1개만 저장 가능 — B11(멀티 등록) 미해결.

2. `Product.optionName`(String?) + `Product.optionValues`(Json?, 문자열배열)로
   단일 옵션축을 이미 저장 중. 실측 예: `optionName:"색상"`,
   `optionValues:["화이트","핑크","블루"]`. **옵션별 대체상품 매칭(B13)은
   이 optionValues의 각 값과 매칭되는 개념으로 설계해야 함.**

3. 디스코드 품절알림(`src/lib/notifications/discord-builder.ts`
   `StockAlertProduct.alternatives` 필드)은 **이미 존재**하지만, 실제 발송
   코드(`src/app/api/cron/daily/route.ts` L205)에서 `alternatives: []`로
   **하드코딩**돼 있어 항상 빈 배열만 감. substituteInfo를 여기 연결하면
   기존 UI(discord-builder.ts의 altLines 렌더링 로직)를 재사용 가능 —
   **신규 UI 설계 불필요, 데이터 연결만 하면 됨.**

4. 재고 크론(`vercel.json`)은 `inventory-sync: "0 0 * * *"` — **1일 1회**.
   B15가 요구하는 데일리 2회 미구현. Gemini 정리본 권고 시간대(오전9시·
   오후2시 KST)는 **근거 없는 추정치**로 취급 — 채택 시 "왜 이 시간대인지"를
   운영자에게 되묻거나, 최소한 근거 없는 추정임을 커밋 메시지에 명시할 것
   (#357 하드코딩 기본값 주석신뢰금지 원칙 준수).

## 설계 확정 — 데이터 shape (신규 마이그레이션 불필요, JSON 컬럼 재사용)

```typescript
// substituteInfo JSON shape v2. version 필드 없는 기존 레코드는 v1(레거시)로
// 판정 — 하위호환 필수, 기존 단건 데이터 유실 금지.
interface SubstituteInfoV2 {
  version: 2;
  // B11 — 우선순위가 있는 다중 대체상품. priority 오름차순이 폴백 순서
  // (1번 품절 시 2번 자동 안내 — Gemini 제안 "무한 안전망", 실측상 타당).
  substitutes: Array<{
    priority: number;
    substituteProductId?: string | null;
    substituteName: string;
    substituteNote?: string | null;
    sourcingUrl?: string | null;
    sourcingCode?: string | null;
  }>;
  // B13 — 옵션값(Product.optionValues의 원소)별 매칭. "화이트 주문 시 이
  // 상품으로 발주" 케이스. optionValue가 optionValues에 없는 값이면
  // 저장 시 경고(오타 방지) — UI 레벨에서 select/자동완성으로 강제 권장.
  optionMatches?: Array<{
    optionValue: string;
    substituteProductId?: string | null;
    substituteName: string;
    substituteNote?: string | null;
  }>;
  lowStockThreshold?: number | null;
}

// 레거시 v1 (기존 그대로, version 필드 없음) — 읽기 시 v2로 변환해 렌더.
interface SubstituteInfoV1Legacy {
  hasSubstitute: boolean;
  substituteProductId?: string | null;
  substituteName?: string | null;
  substituteNote?: string | null;
  sourcingUrl?: string | null;
  sourcingCode?: string | null;
  lowStockThreshold?: number | null;
}
```

**하위호환 변환 규칙**: `substituteInfo.version !== 2`이면 v1로 간주,
`substitutes: [{priority:1, ...v1의 필드}]` 1개짜리 배열로 즉시 변환해
취급(저장 시에는 v2로 다시 씀 — lazy migration, 별도 배치 불필요).

## 작업 항목 (순서 중요 — 의존성 있음)

### 1. `substitute_info` 자료구조 v2 확장 (선행, 다른 항목의 기반)
- 위 타입을 `SubstituteEditor.tsx`가 참조하는 공용 타입 파일로 분리
  (예: `src/lib/products/substitute-types.ts`) — 프론트·백엔드·크론이 모두
  같은 정의를 import (#62 단일 권위, 타입 중복 금지).
- v1→v2 변환 헬퍼 함수 하나로 통일(`normalizeSubstituteInfo(raw): SubstituteInfoV2`).
  이 함수를 SubstituteEditor 로드 시, API route 응답 시, 크론 조회 시 전부 재사용.

### 2. B11 — SubstituteEditor UI를 다중 등록 가능하게 확장
- `substitutes` 배열을 리스트 UI로(추가/삭제/우선순위 드래그 또는 순번 입력).
  기존 단일폼 UX(앱상품피커·카테고리추천·URL/코드 입력)는 그대로 각 행에 재사용.
- 저장 API(`/api/products/[id]/substitute` PUT)가 v2 shape 그대로 받아 저장.

### 3. B13 — 옵션값별 매칭 UI + 주문 알림
- `Product.optionValues`가 있는 상품만 "옵션별 대체상품 매칭" 섹션 노출.
  optionValues 배열을 select로 제공(오타 방지, #368 유사원칙 — 자유입력은
  오염 위험).
- **주문 알림**: "화이트 상품은 이 상품으로 주문하세요" 알림 트리거 지점을
  먼저 찾을 것 — 현재 주문 수신 흐름(`/api/cron/order-sync` 등)에 옵션값이
  넘어오는지 실측 확인 후, 매칭되면 디스코드 알림(신규 embed 타입 또는
  기존 재사용) 발송. **주문 관련 로직은 비가역 발송 위험 — 실제 운영
  디스코드로 실발송 전 반드시 dry-run 모드로 먼저 검증(#46).**

### 4. B15 — 데일리 알림 실데이터 연결 + 크론 빈도
- `cron/daily/route.ts` L205 `alternatives: []` → 해당 상품의
  `substituteInfo.substitutes`(normalizeSubstituteInfo 거친 v2)를
  `StockAlertProduct.alternatives` shape(`alt_product_name`,
  `platform_code`, `platform_url`)로 매핑해 실제로 채움.
- **1번 대체상품마저 품절인 경우** — Gemini 제안 "2차 방어선 감지"는 타당한
  아이디어. substitutes 각각의 실시간 재고(자기 자신도 Product이므로
  inventory_snapshots 조회 가능)를 확인해 전부 품절이면 등급을 높인
  경고(예: 기존 STOCK_ALERT 색상과 구분되는 강조)로 표시. 신규 등급을
  만들 때는 discord-builder.ts의 기존 색상 팔레트/embed 타입 패턴 재사용.
- **크론 데일리 2회**: vercel.json에 두 번째 스케줄 추가(cron 무료한도·
  Vercel Hobby plan 제약 확인 후 — 유료 플랜 필요할 수 있음, 확인 안 되면
  Desktop에 보고). 정확한 실행 시각은 위 "근거없는 추정치" 주의사항 참고.
