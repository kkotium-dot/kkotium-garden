## 2026-08-06 (Desktop) 신규 원칙 #332

### #332 — 화면에 노출되는 값이 내부 코드면 표시 계층에서 한글 라벨로 변환한다 (코드값은 데이터로만 유지)

플랫폼 코드·enum·상태값 같은 내부 식별자를 화면에 **그대로** 렌더하면 셀러(운영자)는 그 약어가 무슨 뜻인지 즉시 알 수 없다. 화면 문구는 개발자 은어가 아니라 셀러 실무 용어여야 한다(#317). 내부 코드값은 데이터 계약(DB·API)에 그대로 두고, **표시 계층에만 한글 라벨 매핑 함수**를 둔다.

**사건(2026-08-06, 소싱 위젯 UX 종합점검 중 프로덕션 실측)**: 소싱 위젯 도매 매칭 목록의 플랫폼 배지가 내부 코드 `DMM`·`DMK`를 그대로 노출했다(DMM=도매매, DMK=도매꾹). 셀러는 이 약어로 어느 도매처인지 알 수 없다. 카드·드로어 두 화면, 배지·헤더 4곳에서 동일 노출.

**근본 수정**: `getPlatformLabel(platform)` 단일 헬퍼(카드·드로어 공유, #62 단일 권위)를 두어 DMK→도매꾹(초록)·DMM→도매매(빨강)로 변환. 배지 `{w.platform}` → `getPlatformLabel(w.platform).label`. **DB·API의 코드값('DMM'|'DMK')은 무변경** — 데이터 계약은 그대로 두고 사람이 읽는 표현만 표시 계층에서 만든다.

**연장 발견(#325 계열, 빈 괄호)**: 배포 후 프로덕션 검증에서 헤더가 "도매 매칭 ()"처럼 빈 괄호로 나왔다. 원인은 헤더가 참조하던 요약 필드 `wholesalePlatforms`를 API가 실제로는 안 채운다는 것(항상 undefined) — 실제 플랫폼 정보는 목록 데이터 `wholesaleMatches[].platform`에 있었다. **죽은 요약 필드 대신 실제 목록 데이터에서 유도**(new Set 고유화 후 라벨 매핑)하고, 없으면 괄호 자체를 생략하도록 수정.

**규칙**:
1. 화면에 나가는 값이 내부 코드/enum/상태값이면 표시 계층에 라벨 매핑 함수를 두고, 여러 화면이 그 단일 함수를 공유한다(#62·#317). 코드값 자체는 DB·API에 그대로 유지한다(데이터 계약 무변경).
2. 표시용 "요약 필드"(예: platforms 배열)를 만들었으면 그 필드가 실제로 채워지는지 확인한다. 안 채워지면 죽은 필드다(#325) — 대신 실제 목록 데이터에서 유도한다.
3. 데이터가 없을 때 "(  )"·"[]" 같은 빈 껍데기를 남기지 말고 해당 장식(괄호 등) 자체를 생략한다.
4. 이런 표시 결함은 tsc/build로 안 잡힌다(타입은 맞고 렌더 문자열만 이상). **프로덕션 브라우저 실측**으로만 확인된다(#45/#275) — 배포 후 실제 화면을 눈으로 본다.

2. 경로별 `group_by: requestPath` 또는 `query`로 필터링해 "그 경로가 예정 시각에 실제로 찍혔는지" 직접 대조한다 — 등록 상태(dashboard "Enabled")만으로 실행을 단정하지 않는다.

## 2026-08-10 (Code) 신규 원칙 #334~#335

### #334 — AI/캐시 파이프라인에서 생성 로직을 고쳐도 이미 저장된 캐시는 안 바뀐다 — 캐시가 생성 호출보다 먼저 조회되는 구조인지 항상 확인한다

생성 로직(AI 프롬프트 등)의 버그를 고쳐도, 그 결과를 캐싱해 재사용하는 구조라면 **이미 캐시에 저장된 과거 오답은 새 로직이 실행조차 되지 않아 계속 서빙된다.**

**사건(2026-08-10, 씨앗심기 카테고리 "가구/인테리어" 대량 오분류 수정 중 발견)**: `api/category/suggest/route.ts`는 `dome_category_cache`(name_hash/dome_code)를 AI 호출보다 먼저 조회한다. AI 프롬프트의 강제 폴백 지시("모르면 가구/인테리어로")를 삭제했지만, 이미 스캔된 적 있는 상품명은 캐시 히트로 즉시 반환되어 **수정 전 프롬프트가 만든 오답을 그대로 계속 서빙**했다(브라우저 curl 재현 중 `cacheHit: "name_hash"` 확인, 신규 상품명으로 바꾸자 비로소 새 프롬프트 경로 확인됨).

**규칙**:
1. 캐시를 쓰는 생성 파이프라인의 버그를 고칠 때는 "캐시가 생성 호출 앞에 있는지" 코드 흐름을 반드시 확인한다. 앞에 있다면 수정은 **신규 입력에만** 적용되고, 기존 캐시 오염은 별도 정리(무효화/재계산)가 필요하다 — 코드 수정 하나로 끝났다고 보고하지 않는다.
2. 검증 시 캐시 히트 여부(`cacheHit` 필드 등)를 반드시 확인한다. 캐시 히트로 "고쳐진 것처럼" 보이거나 "안 고쳐진 것처럼" 보이는 결과 둘 다 착시일 수 있다 — 신규(캐시 미스) 입력으로 재현해야 실제 수정 효과를 검증한 것이다.
3. 캐시 오염 정리(기존 오답 행 삭제/재계산)는 DB 쓰기이므로 운영자 결정 없이 임의 실행하지 않는다 — 발견 사실만 보고하고 방침은 위임한다.

### #335 — "정보가 리셋된다"는 UX 버그는 복원(hydrate) 로직이 아니라 저장(write) 로직의 데이터 유실이 원인일 수 있다 — 저장 경로가 실제로 무엇을 쓰는지부터 확인한다

폼을 다시 열었을 때 필드가 비어 보이면 보통 "복원 로직이 그 필드를 안 읽는다"고 의심하기 쉽지만, **애초에 저장 시점에 그 필드가 DB에 기록되지 않았을 수 있다.** 복원 로직은 무죄이고 저장 로직이 원인인 경우, 복원 코드를 아무리 고쳐도 증상은 그대로다.

**사건(2026-08-10, 씨앗심기 이동 시 정보/이미지 리셋 버그 조사)**: `products/new/page.tsx`의 `?edit=` 로더(`productFormHydrate`)는 DB에 있는 값을 빠짐없이 정확한 컬럼명으로 복원하고 있었다(버그 없음). 실제 원인은 `api/products/import/route.ts`가 네이버 원상품 상세를 가져오면서 `name`/`salePrice`/`mainImage`/`status` **4개 필드만 골라 저장**하고, 이미 응답에 들어있던 카테고리·설명·추가이미지·태그를 전부 버리고 있었던 것 — 복원할 데이터 자체가 DB에 없었다.

**규칙**:
1. "저장했다가 다시 열면 비어있다" 류 버그는 먼저 DB를 직접 조회해(또는 저장 API 응답을 확인해) **그 필드가 애초에 저장돼 있는지**부터 확인한다. 있는데 안 읽으면 복원 버그, 없으면 저장 버그 — 두 원인은 수정 위치가 완전히 다르다.
2. 외부 API(네이버 등) 응답을 DB로 매핑하는 import/ingestion 라우트를 고칠 때는, 응답에 이미 존재하는 필드 중 **앱 스키마와 형식이 100% 동일한 것만** 추가로 채운다(예: 네이버 leafCategoryId → 앱 naverCategoryCode는 같은 코드 체계라 안전). 코드 체계가 다른 필드(원산지 코드, AS 정보 등)는 오매핑 위험이 있으므로 형식 불일치가 확인되기 전엔 채우지 않는다.

## 2026-08-10 (Code) 신규 원칙 #336

### #336 — 여러 층위(AI·검증·폴백)가 얽힌 분류 버그는 각 층위를 임시 로그로 직접 찍어 어느 층위인지 확정한 뒤 고친다 — 가장 정교해 보이는 층위가 범인이라고 추정하지 않는다

카테고리 추천처럼 "AI 호출 → 검증/보정 로직 → 폴백 규칙"이 순서대로 얽힌 파이프라인에서 오답이 나오면, 가장 복잡해 보이는 중간 로직(fuzzy 매칭 등)을 의심하기 쉽다. 하지만 **실제로는 훨씬 단순한 층위(폴백 규칙 데이터 자체, 또는 AI의 단순 사실 오답)가 원인일 수 있다** — 추정으로 고치면 엉뚱한 층위를 건드리고 진짜 원인은 남는다.

**사건(2026-08-10, "반려동물 자동급식기"가 계속 "가구/인테리어"로 나오는 잔여 오분류 조사)**: Desktop은 `validateSuggestion()`의 fuzzy 매칭(d1 exact, d2 char-overlap 50%)이 오답을 통과시키는 것으로 의심했다. Code가 AI 원본 응답과 검증 전/후 값을 임시 `console.warn`으로 찍어 재현한 결과, **fuzzy 매칭은 전혀 관여하지 않았다** — AI가 진짜로 실재하는 카테고리("가구/인테리어>주방가구>그릇장/컵보드")를 답해 1번 exact-match 분기로 바로 통과한 것이었다. 진짜 원인은 완전히 다른 곳: `FALLBACK_RULES`(AI 실패 시 안전망)의 반려동물 규칙이 `d1:'반려동물'`이라는, DB에 아예 존재하지 않는 카테고리 축을 가리키고 있어 안전망 자체가 매번 무력화되고 있었다(실제 축은 `생활/건강>반려동물`). fuzzy 매칭 코드는 손댈 필요가 없었다.

**규칙**:
1. 다층 파이프라인의 분류/판정 버그는 각 층위의 입출력을 임시 로그(작업 후 제거)로 실제로 찍어서 확정한 뒤 고친다. "이 로직이 복잡하니 여기가 범인일 것"이라는 추정만으로 코드를 고치면, 진짜 원인(더 단순한 데이터 테이블의 오류 등)을 놓친다.

떠서, 두 컬럼 다 outgoing PUT 페이로드 어디에도 안 들어간다(내부 완결성
점수용으로만 읽힘) — 화이트리스트가 추적은 하지만 실제로 네이버에 반영되지
않는 필드다.

**규칙**:
1. "네이버 API에 X라는 필드/개념이 있을 것이다"는 절대 추정하지 않는다.
   `getProduct()`(또는 등록/수정 응답)를 실제로 호출해 `JSON.stringify`로
   구조를 직접 확인한 뒤 매핑한다(#82의 구체적 실행 방법). 가능하면 발행된
   상품 여러 건을 GET해서 필드 존재 여부가 상품마다 우연이 아닌지 확인한다.
2. 응답에 없는 필드는 "아직 못 찾았다"가 아니라 "네이버가 이 개념 자체를
   구조화된 형태로 주지 않는다"는 결론일 수 있다 — 특히 여러 개의 로컬
   컬럼(hookPhrase/detail_image_url/detail_images/description)이 발행
   시점에 하나의 HTML(`detailContent`)로 합쳐지는 구조라면, 그 역방향
   복원은 파싱 추측이니 시도하지 않는다.
3. dirty-field 화이트리스트처럼 "이 필드가 바뀌면 네이버에도 반영된다"고
   운영자에게 보여주는 UI가 있다면, 그 필드가 실제로 payload 빌더(`build
   NaverProductPayload` 등)의 어느 컬럼을 읽는지 반드시 추적해 폼 저장
   컬럼과 일치하는지 확인한다(#340 연장) — 일치하지 않거나 payload에
   아예 안 들어가면 운영자에게 "바뀜"이라고 잘못 알리는 셈이니 발견 즉시
   기록하고(수정은 별도 스코프 판단), 방치하지 않는다.

## 작업원칙 #343 — Hobby 크론은 "시각"이 아니라 "시간대"로 발동한다. 창이 닫히기 전의 미수신은 실패가 아니다 (2026-08-20)

**사건**: 소싱 알림이 8일간 "안 온다"고 판정돼 5개 가설을 세우고 전부 기각했다. 실제로는 rev120의 self-fetch 제거 수정이 처음부터 작동하고 있었고, 크론은 매일 정상 실행되고 있었다. `cron_invocation_log` 실측: `/api/cron/sourcing-daily | 08-20 08:55:50 KST | auth_ok=t | ok | 6719ms`.

**원인**: Vercel Hobby 크론은 `0 23 * * *`을 23:00~23:59 UTC(08:00~08:59 KST) **사이 임의 시점**에 발동한다. 그런데 형제 크론(`cron/daily`)이 23:0x에 찍히는 걸 보고 "소싱도 같은 시각"이라 전제한 뒤, **창이 끝나기 12분 전인 08:47에 확인하고 "재발"로 판정**했다.

**규칙**:
- 스케줄러 미수신을 판정하려면 **발동 창이 완전히 닫힌 뒤**에 본다.
- 형제 크론의 실행 시각을 다른 크론의 기준으로 삼지 않는다(플랫폼이 부하 분산한다).
- 관측 수단 없이 가설만 반복하지 않는다. `cron_invocation_log` 같은 **자체 계측을 먼저 심는다**. 플랫폼이 이력을 안 주면 우리가 기록한다(#337의 벽을 뚫는 방법).

## 작업원칙 #344 — 완료 판정은 "사용 지점에서의 증명"으로만 한다. tsc 통과는 완료가 아니다 (2026-08-20)

**사건**: 이틀 사이 같은 유형의 실패가 5회 발생했다. 전부 작업은 실제로 했고 코드도 옳았는데 효과가 0이었다.
- F1 커밋 누락 — KST 유틸 11파일·수수료 15파일이 worktree에 미커밋 방치
- F2 병합 누락 — 커밋·push는 됐으나 브랜치에만 존재, main은 옛 코드 그대로
- F3 연결 누락 — 8렌즈·`searchad-volume.ts`가 존재하나 호출부 0건
- F4 데이터 누락 — `dropship-fitness.ts`가 완벽하나 `category_id`가 전 상품 NULL이라 전부 기본값
- F5 문서 미동기화 — 설계안이 Desktop 로컬에만 있어 Code가 착수 불가

**규칙**: 완료 보고 전 5게이트를 **명령 실행 결과로** 증명한다.
1. **커밋** — `git status --porcelain` 비어 있고 해시를 보고에 명시. **해시 없는 완료는 완료가 아니다.**
2. **병합** — `git merge-base --is-ancestor <hash> origin/main`. 브랜치 커밋은 보존이지 반영이 아니다.
3. **연결** — 새 모듈의 호출부를 grep으로 증명. 호출부 없는 모듈은 죽은 코드다(#292 사전 차단판).
4. **데이터** — 로직이 읽는 컬럼의 실제 채움률을 센다. 전 건이 기본값이면 그 로직은 작동하지 않는 것이다.
5. **실행** — 실제로 돌리고 출력값을 원문 그대로 보고에 붙인다. 못 돌렸으면 "못 돌렸다"고 명시하고 검증 스크립트를 인계한다.

**전문**: `docs/playbook/COMPLETION_GATE.md` (보고 템플릿·안티패턴·검증 우선순위 포함)

## 작업원칙 #345 — 문서를 근거로 인계할 때는 커밋·push 후 해시와 함께 넘긴다 (2026-08-20)

**사건**: Desktop이 `PRODUCT_CATEGORY_BACKFILL` 설계안을 작성하고 "정독하라"고 인계했으나, 커밋하지 않아 Code 워크트리에서 파일이 보이지 않았다.

**규칙**:
- 설계안·리서치·인계 문서도 **코드와 동일하게 커밋·push해야 다른 레인이 읽는다.**
- 인계받은 쪽은 문서가 없으면 **요약만 보고 착수하지 말고 부재를 먼저 보고한다.** (2026-08-20 Code의 대응이 모범 사례 — 검증 불가한 요약으로 움직이지 않아 잘못된 전제의 작업을 막았다)
- 문서 레인(Cowork)도 G1·G2 게이트 적용 대상이다.

## 작업원칙 #346 — 분류는 "생성"이 아니라 "선택"으로 만든다. 정답지가 있으면 오분류는 구조적으로 불가능해진다 (2026-08-20)

**배경**: 네이버 카테고리는 오지정 시 미지정보다 큰 페널티를 받는다(적합도=카테고리 선호도, 리서치 항목1). AI에게 카테고리 문자열을 생성시키면 네이버에 없는 값이 나올 수 있다.

**실측**: `src/lib/naver/naver-categories-full.ts`에 2026-07-09자 네이버 공식 XLS 기반 **5,021엔트리**(D1 11개, D4까지 3,475개, 중복 code 0건)가 이미 존재한다.

**규칙**:
- 유한한 정답 집합이 존재하는 분류 문제는 **생성이 아니라 선택**으로 설계한다.
- 3단 구조: ① 규칙으로 후보 압축 → ② AI는 후보 **안에서만** 선택 → ③ 선택값의 실재를 강제 검증.
- 검증 실패 시 **저장하지 않고 `needs_review`**. 추측으로 채우지 않는다.
- 이 원칙은 카테고리뿐 아니라 브랜드·속성·단위 등 마스터 데이터가 있는 모든 분류에 적용한다.

## 작업원칙 #347 — 세션 시작 시 워크트리·lock 위생을 확인한다. 크래시 잔재가 다음 세션의 git 명령을 조용히 실패시킨다 (2026-08-27)

**사건**: 2026-08-20 크래시로 남은 `.git/HEAD.lock`·`.git/index.lock`(0바이트)이 이후 여러 세션 동안 방치됐다. 동시에 `git worktree list`의 워크트리 8개 중 5개가 이미 main에 완전 반영(ahead=0)됐는데도 정리되지 않고 남아있었고, 그중 3개는 "정리 대상"으로 보였지만 실제로는 미커밋 잔재(중복 `" 2.json"` 파일, 이미 아카이브된 내용의 staged diff, 미추적 로컬 설정)를 품고 있어 무심코 지웠으면 손실 여부를 확인 못 할 뻔했다.

**규칙**:
- 세션 시작 시(또는 이번처럼 위생 점검 지시 시) `.git/*.lock` 파일의 존재·크기·mtime을 확인하고, 살아있는 git 프로세스가 없음을 `ps`로 확인한 뒤에만 제거한다.
- `git worktree list`로 워크트리를 감사할 때 **ahead/behind 커밋 수만으로 판단하지 않는다** — 각 워크트리에서 `git status --short`로 미커밋(staged/untracked 포함) 여부를 반드시 함께 확인한다.
- ahead=0이어도 미커밋 변경이 있으면, 그 내용이 이미 main 등 다른 곳에 존재하는 중복인지(`grep`으로 원문 대조) 확인하기 전엔 삭제하지 않는다.

## 작업원칙 #348 — 외부 AI 모델명은 살아있는 의존성이다. 공급자가 조용히 폐기할 수 있고, 그 순간 관련 기능 전체가 침묵한다 (2026-08-27)

**사건**: UCE(Universal Category Engine) 세션에서 `category/suggest`의 `usedAI:false`를 코드 버그로 의심하고 파싱 로직을 개선했으나, 프로덕션 런타임 로그(`vercel logs`) 실측 결과 진짜 원인은 `GROQ_API_KEY`도 파싱도 아니었다 — Groq가 `llama-3.3-70b-versatile`을 카탈로그에서 완전히 제거해 모든 호출이 404였다(`GET /v1/models` 실측으로 확인, 대체 모델도 없이 그냥 사라짐). 같은 하드코딩 모델명을 쓰던 `sourcing-recommender.ts`의 `llama-3.1-8b-instant` 호출도 같은 이유로 동시에 죽어 있었다 — 카테고리 제안 하나만의 문제가 아니라 앱 전역 Groq 의존 기능(SEO 키워드·제목·설명·소싱 인사이트)이 전부 침묵하고 있었다.

**규칙**:
- 모델명은 라이브러리 버전처럼 **시간이 지나면 깨질 수 있는 외부 의존성**이다 — 코드에 흩어 하드코딩하지 말고 단일 상수(`GROQ_MODEL` 같은)로 격리해, 교체가 grep 한 번으로 끝나게 한다.
- AI 의존 기능이 원인 불명으로 침묵/저품질 결과를 낼 때, **파싱·프롬프트를 의심하기 전에 모델 자체의 생존을 먼저 확인**한다 — `GET {provider}/v1/models`로 현재 카탈로그에 그 모델명이 실제로 있는지 찍어본다. 이게 최우선 의심 대상이어야 하는 이유는 조사 비용이 가장 싸고(API 호출 1번), 발생 시 영향 범위가 가장 크기 때문이다(그 모델을 쓰는 모든 기능이 한 번에 죽는다).
- 프로덕션 로그 문구를 코드의 최신 문구와 대조한다 — 로그가 옛 에러 텍스트를 그대로 뱉고 있다면 애초에 최신 코드가 배포되지 않았을 가능성도 함께 검증한다(#350과 함께 적용).

## 작업원칙 #349 — AI에 의존하는 기능은 결정론적 매칭을 1순위로 두고 AI는 실패했을 때만 보조로 부른다 (2026-08-27)

**배경**: `category/suggest`는 원래 "AI 우선 → 실패 시 하드코딩 57건 폴백" 구조였다. AI가 조용히 죽어도(#348) 알아채기 어렵고, 하드코딩 폴백은 유지보수 대상이 늘어나며 커버리지가 작았다.

**실측**: 마스터(`NAVER_CATEGORIES_FULL`, 5,021개 리프)와 상품명을 직접 substring/synonym-split 매칭하는 결정론적 매처(`category-deterministic-matcher.ts`)로 전면 교체한 뒤, 프로덕션 실호출 20종(카탈로그 10 + 카탈로그 밖 10: 달항아리·수세미·우산꽂이 등)이 전부 `usedAI:false`로 유효 카테고리를 반환했다 — AI를 한 번도 부르지 않고도 100% 커버, 비용 0.

**규칙**:
- 유한한 정답 집합(마스터 데이터)이 있는 분류/매칭 문제는 AI보다 **결정론적 매칭을 1순위**로 두고, AI는 결정론적 매칭이 완전히 실패했을 때만 보조로 강등한다(#346의 "생성이 아니라 선택" 원칙의 구체적 배선 패턴).
- `usedAI:false`는 실패 신호가 아니라 **성공 신호일 수 있다** — 어떤 경로로 답을 찾았는지(`source` 필드 등)로 판단하지, AI 호출 여부만으로 성패를 판단하지 않는다.
- 결정론적 매처가 마스터에서 직접 파생되면, 마스터가 갱신될 때(UCE-5류 재생성 파이프라인) 별도 유지보수 없이 자동으로 최신화된다 — 하드코딩 규칙 목록은 항상 이 방식으로 대체를 검토한다.
- **단서(UCE-7, 2026-08-27) — 저신뢰 결정론은 AI 교차확인**: "결정론이 뭐라도 반환하면 AI 미호출"을 무조건 적용하면 결정론의 **오답**을 교정할 기회가 없다(실측: `실리콘주걱`→접착용품>실리콘, `차량용방향제`→여가/생활편의>원데이클래스처럼 존재하는 카테고리로 틀리게 매칭). 결정론 결과가 (a) 약한 티어(전체 리프 정확매칭이 아닌 d3-only/역포함 폴백)이거나 (b) 최고점이 임계 미만이거나 (c) 2위 후보가 다른 d1에서 근소 차로 붙어있으면, **그 슬라이스에 한해서만** Groq을 교차확인으로 호출해 `usedAI:true`로 승격한다 — 고신뢰 결정론(정확 리프 매칭)은 여전히 AI 미호출·비용 0을 유지한다(구현: `src/app/api/category/suggest/route.ts` `isDeterministicLowConfidence`, 설계: `docs/design/UCE7_MATCH_QUALITY_2026-08-27.md`).

## 작업원칙 #350 — 표면적인 "실패처럼 보이는 결과"(source:fallback, 빈 응답 등)를 실측 없이 실패로 단정하지 않는다. 그 값을 만든 코드의 반환 조건을 먼저 확인한다 (2026-08-27)

**사건**: `kkotti-comment` 같은 AI 응답 라우트가 특정 입력(예: 대상 상품 0건)에서 폴백/빈 값을 반환하는 것을 보고 "AI 실패"로 오판할 뻔했다 — 실제로는 그 조건에서 폴백을 반환하도록 **의도적으로 설계된 정상 경로**였고, 상품이 있는 입력으로 다시 호출하면 `source:groq`(실측)로 정상 동작했다.

**규칙**:
- `usedAI:false`·`source:fallback`·빈 배열/문자열 같은 "실패처럼 보이는" 응답 필드를 마주치면, 그 값을 **어떤 코드 경로가 왜 반환했는지**(가드 조건·early return)를 먼저 읽는다 — "실패했나 보다"라고 추측(#82 위반)하지 않는다.
- 같은 엔드포인트를 **입력을 바꿔가며 재현**해 "이 입력에서는 정상적으로 폴백" vs "이 입력에서는 원래 성공해야 하는데 실패"를 구분한다.
- #348(모델 생존 확인)·#349(결정론 우선)와 함께 적용: 표면 신호(usedAI/source) → 코드 반환조건 확인 → (필요시) 외부 의존성 생존 확인 → 런타임 로그 실측, 순서로 좁혀간다(`docs/playbook/AI_DEPENDENCY_DIAGNOSIS.md` 참조).
- 워크트리·브랜치 삭제, `.git/*.lock` 제거처럼 되돌리기 어려운 정리 작업은 **사용자 승인 후에만** 실행한다(safety 원칙과 동일선상).

## 작업원칙 #351 — 캐시 있는 로직을 수정할 때는 캐시 무효화가 완료조건이다. 코드수정 ≠ 실효 (2026-08-27)

**사건(UCE-7)**: `category-deterministic-matcher.ts` + `category/suggest/route.ts`를 고치고 main 병합·프로덕션 배포까지 확인했는데, 프로덕션 실측에서 "차량용방향제"·"칫솔살균기"·"전동칫솔"·"요가매트" 4건이 **여전히 옛 오답**을 반환했다. 원인은 `category_mappings`(name_hash 학습 캐시)에 옛 코드가 저장해 둔 오답 로우가 캐시 히트로 그대로 서빙된 것 — 코드는 100% 고쳐졌고 배포도 됐는데, **캐시가 "고쳐지기 전 세계"를 기억**하고 있었다. 1차 조치로 해당 로우 4건을 수동 `DELETE`했지만, 이는 **이번 건에서만 통하는 임시방편**이다 — 다음에 매처 로직을 또 고치면 같은 사고가 반복된다.

**근본 수정**: `dome-category-cache.ts`에 `CATEGORY_MATCH_LOGIC_VERSION` 상수를 신설하고, 캐시 저장/조회 키(`normalizeKey`)에 `.v<버전>` 접미사로 항상 포함시켰다. 매처의 스코어링·티어·AI 교차확인 게이트 등 **"같은 입력에 대해 다른 정답을 낼 수 있는" 로직**을 고칠 때마다 이 숫자를 올리면, 옛 버전 접미사가 붙은 로우는 새 조회 키와 영영 매치되지 않아 **자동으로 재계산**된다(수동 DELETE 사냥 불필요, 옛 로우는 그냥 고아로 남아 무해하게 방치).

**규칙**:
- **캐시가 낀 로직을 수정할 때, "코드 수정 완료"와 "실제 효과 발생"은 별개 사건이다.** 캐시가 있다면 그 캐시를 어떻게 무효화할지가 완료조건의 일부다 — 매 배포마다 수동으로 캐시를 뒤지고 지우는 절차는 **재발이 예정된 미봉책**이지 해결이 아니다.
- 판별법: "이 로직의 출력을 저장해 두고 재사용하는 캐시/학습 테이블이 있는가?"에 예라면, 로직을 고치는 커밋에는 **버전 태그 방식의 무효화(또는 TTL·명시적 캐시 클리어 스크립트)를 함께 넣는다** — 사람이 매번 기억해서 지우는 것에 의존하지 않는다.
- 완료 보고 전 **캐시 히트 경로를 직접 실측**한다(`cacheHit` 같은 응답 필드, 또는 DB 조회) — 응답이 맞아 보여도 그게 "새 로직이 방금 계산한 것"인지 "옛 로직이 예전에 캐싱해 둔 것"인지 구분 없이는 완료로 인정하지 않는다(#350과 연결 — 표면 신호만으로 성패를 판단하지 않는다).
- #349(결정론 우선)·#350(표면 신호 재검증)과 한 세트: 결정론적 매칭·학습 캐시처럼 "정답을 저장해 재사용"하는 설계는 강력하지만, **그 저장소가 로직 버전과 묶여 있지 않으면 캐시가 곧 회귀의 온상**이 된다.


## 작업원칙 #352 — 테스트 green ≠ 전수 안전. 비가역 쓰기는 "임의 표본 전수 dryRun"을 통과해야 한다 (2026-08-27)

**사건(category_id backfill)**: `naver_categories` 마스터 적재 후, 상품의 과거 `naverCategoryCode`(오라벨)를 그대로 FK 연결한 backfill이 아이스트레이→"홍합", 디퓨저→"교자상" 같은 오라벨을 만들었다. 이를 고치려 UCE 매처 기반 resolver + 정합성 테스트(`test:category-integrity`)를 만들어 **5/5 → 16/16 green**을 받았다. 그런데 Desktop이 **--apply 전 dryRun을 실제로 돌려보니**, 전 상품 15종 중 4건이 오히려 **새 오분류로 개악**될 상황이었다(듀얼가습기→"완구>기차", 달항아리→현재 맞는 "도어벨"에서 틀린 "도서>인테리어"). resolver를 confidence 게이트로 보수화(애매하면 NULL)한 뒤에도, **카탈로그 밖 임의 20종 테스트에서 무선청소기→"공구", 물티슈→"반려동물" 등 오분류가 남았다.**

**핵심 교훈 3가지**:
1. **테스트가 커버한 표본 ≠ 실제 전수.** 정합성 테스트가 16/16 green이어도, 그 테스트에 든 케이스만 검증한 것이다. "green = 안전"이 아니라 "green = 이 케이스들만 안전"이다. 진짜 검증은 **카탈로그 밖 임의 상품 20~30종 전수**로 한다(기둥 3의 "임의 표본" 강화).
2. **dryRun은 비가역 쓰기의 필수 방어선.** `--apply`(DB 직접 쓰기) 전에 dryRun으로 "무엇이 어떻게 바뀌는가"를 전량 출력해 육안 검수한다. dryRun이 "정정하려다 개악"을 배포 전에 잡았다 — dryRun 없는 비가역 쓰기는 금지.
3. **보수화(NULL)로는 근본을 못 고친다.** resolver를 아무리 보수적으로 만들어도(애매하면 비움), 그 아래 **공통 엔진(매처)이 수식어('인테리어')를 핵심명사('달항아리')보다 높게 치는 결함**이 있으면 개악은 계속 난다. 진짜 뿌리는 여러 소비처(backfill·소싱·/api/suggest·발행넛지)가 공유하는 **단일 엔진**이다 — 거기를 고쳐야 전부 풀린다(기둥 2 = 단건 수습 금지).

**규칙**:
- 비가역 데이터 쓰기(DB backfill/migration/일괄 UPDATE) 완료조건 = **① 카탈로그 밖 임의 표본 20종+ 전수 dryRun 오분류 0 + ② 실제 카탈로그 전수 dryRun 개악 0 + ③ 그 케이스들을 회귀 테스트에 고정**. 이 셋을 통과하기 전 `--apply` 금지.
- "green"을 완료로 인정하지 않는다. **green이 검증한 표본의 범위**를 명시하고, 그 밖의 임의 표본으로 재검증한다.
- 개악(원래 맞던 값을 틀리게 바꿈)은 미개선(빈손 유지)보다 나쁘다. 확신 없으면 **NULL 유지(정직)**가 개악보다 낫다(#350 정직표시와 연결).
- 여러 화면/경로가 같은 판정을 쓰면, 소비처마다 우회 보수화하지 말고 **공통 엔진 한 곳**을 고친다(#295 단일 권위·#62 시스템 수정).
- CORE_WORKING_PRINCIPLES 기둥 1(구조≠내용: 테스트 green은 구조, 전수 정확은 내용)·기둥 3(임의 표본 전수)의 구체 적용 사례.


## 작업원칙 #353 — 자동분류는 "고신뢰만 자동, 애매하면 사람 확인". 완벽한 자동화보다 안전한 반자동 (2026-08-27)

**사건(카테고리 매처)**: 카테고리 매처 정확도를 100%로 올리려 여러 세션에 걸쳐 매처를 반복 수정했으나, 임의 30종 전수 dryRun 결과 정확도 77%(정확17·NULL8·오분류5)에서 벽에 부딪혔다. 매처를 6종 고치면 5종이 새로 터지는 **무한 두더지잡기** — '사료'가 관상어사료(d3 완전일치)에 낚여 강아지사료(부분매칭)를 이기는 등, 부분토큰 매칭의 태생적 한계다. Code에 매처를 계속 갈게 하는 건 ROI가 낮다고 판단, "고신뢰만 자동 + 애매하면 사람 확인" 반자동으로 전환했다.

**출처 교차검증(2026-08-27)**: 이 전환이 감이 아니라 업계 표준·네이버 공식 방식임을 웹으로 확인:
- 스마트스토어 카테고리는 **한번 등록하면 재수정·변경이 어렵다(비가역)** → 자동 오분류는 치명적. 틀리게 자동입력하느니 비워두고 사람이 확인하는 게 맞다(mangotree/sjnim manual).
- 네이버 상품등록 자체도 **모델명이 정확히 매칭될 때만(고신뢰)** 카테고리를 자동입력하고, 그 값은 변경 불가. 매칭 안 되면 셀러가 직접 선택(dubuplus).
- 업계 관행: **카테고리가 애매하면 네이버쇼핑에 검색해 타사 결과로 확인**한다 = 사람 확인 루프가 표준(sjnim).

**규칙**:
- 자동분류/자동입력 기능의 완료조건은 "정확도 100%"가 아니라 **"오분류 0%(고신뢰만 MATCH, 애매하면 비움)"**이다. 100% 자동보다 **개악 0%**가 우선(#352 개악>미개선의 연장).
- 비가역 대상(스마트스토어 카테고리처럼 되돌리기 어려운 것)일수록 이 원칙이 강하다. 확신 없으면 자동으로 쓰지 말고 **NULL 유지 → 사람 개입큐(UCE-4)로 흘린다**.
- "완벽한 자동화"를 목표로 무한정 엔진을 튜닝하는 것은 새싹셀러 ROI상 함정일 수 있다. 어느 지점에서 **"후보 제시 + 사람 최종선택" 반자동으로 전환**하는 게 매출 레버(발행·SEO·리뷰)에 시간을 쓰는 길이다.
- 판별: "이 자동 결과가 틀렸을 때 되돌리기 어려운가?"에 예라면 → 고신뢰 임계를 높이고 애매한 건 사람에게. 아니오라면 → 자동 폭을 넓혀도 됨.
- 개입점은 이미 있는 것을 쓴다: 매처 후보 → 씨앗심기 UI 후보 3개 → 사람 선택(UCE-4 개입큐). 새 UI 만들지 말고 기존 흐름에 연결.
- CORE_WORKING_PRINCIPLES 기둥 3(개입점 자연스럽게)의 구체 적용. #350(정직표시)·#352(개악>미개선)와 한 세트.


## 작업원칙 #354 — 브랜치/워크트리 상태는 git log(커밋)만이 아니라 working tree(미커밋)까지 봐야 판정된다 (2026-09-02)

**사건(Desktop 오판 2건, Code가 교정)**: category 반자동 작업 중 Desktop이 두 가지를 잘못 판정했다.
1. **"elegant-kirch는 빈 브랜치(커밋0)"** — `git rev-list origin/main..branch`(커밋 이력=구조)만 보고 "비었으니 정리가능"이라 상신. 실제로는 `git status`상 **미커밋 변경 2파일(dashboard-product.ts·DailyPlanWidget.tsx)**이 있었다. Code가 "다른 세션 작업중 상태를 임의로 안 지운다"로 올바르게 멈췄다.
2. **"DailyPlanWidget에 카테고리채우기 뜨는지 실측하라"** — 그 파일은 헤더에 `⚠️ @unmounted(2026-07-22 전수확인)` = **죽은 코드**라 브라우저 실측 자체가 불가능. Code가 발견해 진짜 라이브 화면(/growth UploadReadinessWidget)으로 정확히 리다이렉트했다.

**핵심 교훈**:
- 브랜치가 "비었다/정리가능"을 판정할 때 `git log`(커밋 이력)만 보면 **working tree의 미커밋 변경을 놓친다**. 반드시 `git -C <worktree> status --porcelain`까지 확인한다. 커밋0 ≠ 작업0.
- UI 컴포넌트에 "실측하라"고 인계하기 전, 그 컴포넌트가 **실제 마운트되는 라이브 화면인지** 먼저 확인한다(파일 헤더 @unmounted 주석·라우트 grep). 죽은 코드 실측은 시간 낭비이자 허위 완료의 씨앗.
- 이건 CORE_WORKING_PRINCIPLES 기둥1("구조≠내용·내가 틀릴 수도 있다")의 정확한 실례 — Desktop이 구조(git log)만 보고 내용(working tree/마운트 여부)을 안 봤고, 핑퐁 교차검증(Code)이 교정했다. **레인 간 상호검증이 단일 레인의 오판을 잡는다는 증거.**

**규칙**:
- 워크트리 삭제/정리 상신 전 체크리스트: (1)`git rev-list`(ahead/behind) (2)`git status --porcelain`(미커밋) (3)다른 세션 활성 여부. 셋 다 확인 후에만 "정리가능" 판정.
- 컴포넌트 실측 인계 전: 라이브 마운트 확인(@unmounted 주석·페이지 import grep). 죽은 코드면 진짜 라이브 표면을 지목.
- 클러스터 인덱스 "워크트리·git 위생"에 #354 추가.


## 작업원칙 #355 — autosave/파생 저장은 "실제 변경 시에만". 비가역 행위 직전엔 정합성 게이트 (2026-09-02)

**사건 2건(category_id 발행 직전)**:
1. **재발 버그**: clear-known-wrong로 지운 오라벨(홍합 category_id)이, 편집화면을 **열기만 해도**(아무 클릭 없이) autosave가 stale naverCategoryCode를 재전송 → category_id가 홍합으로 **자동 부활**. 원인: 파생 조건이 "요청에 naverCategoryCode 포함되면"이었고 "실제로 값이 바뀌었을 때"가 아니었음. 수정(41342ef): `updateData.naverCategoryCode !== prevData.naverCategoryCode`일 때만 derive.
2. **발행 직전 오분류**: 발행임박 상품 "라이트 LED 저소음 사무실 가습기"가 category "인테리어소품>조명>LED모듈"로 오분류('LED'가 조명에 낚임). 발행게이트가 이 상충(가습기≠조명)을 못 잡음 → 이대로 발행되면 참사.

**핵심 교훈**:
- **autosave/파생 로직은 "요청에 필드가 있음"이 아니라 "값이 실제로 바뀜"을 조건으로 한다.** 안 그러면 화면을 여는 것만으로 stale 값이 되살아나 애써 고친 데이터가 자동 오염된다. "포함됨 ≠ 변경됨".

**규칙**:

## 작업원칙 #356 — 오라벨 청소는 category_id + naverCategoryCode 둘 다. 발행에 실제 쓰이는 필드를 청소해야 한다 (2026-09-02, 브라우저 실측)

**규칙**:

## 작업원칙 #360 — 반응형(모바일) UI 검증은 OS 창 리사이즈가 아니라 실제 뷰포트 반영 여부를 먼저 확인한다 (2026-09-04)

**사건(B2 검증)**: Claude-in-Chrome `resize_window`(390x844) 요청 후 `getComputedStyle`로 액션바를 확인했더니 `bottom:20px, zIndex:40, className:""` — 수정 전 구버전처럼 보였다. 프로덕션 배포 SHA는 이미 `verify-vercel-deploy.sh`로 정확히 확인된 상태라 "배포 안 됐나?"로 잘못 의심할 뻔했다. 근본원인은 `window.innerWidth`를 직접 찍어보니 여전히 1834px — **`resize_window`가 OS 창 크기만 바꿨고 실제 렌더링 뷰포트(devicePixelRatio 포함)는 반영되지 않았다.** 동일 호출을 재시도하니(414x800) 이번엔 `innerWidth:625, matchesLg:false`로 정확히 반영됐고, 그 상태에서 액션바가 `bottom:76px, zIndex:65`(수정 코드 그대로)로 정상 렌더됨을 확인했다.
**규칙**:

- 모바일 UI 회귀 검증 표준 절차: ① `resize_window`로 목표 폭 요청 → ② `window.innerWidth`/`matchMedia`로 실제 반영 확인(불일치 시 재시도) → ③ 반영 확인 후에만 스크린샷·`getComputedStyle`로 실제 UI 검증 → ④ 필요 시 `getBoundingClientRect()`로 요소 간 겹침(overlap) 여부를 좌표로 정량 확인(육안 스크린샷 판단보다 정밀).
