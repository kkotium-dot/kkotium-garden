## 1. 레인별 담당 (누가 무엇을)

| 레인 | 할 수 있는 것 | 할 수 없는 것 | 대표 작업 |
|---|---|---|---|
| **Desktop** (설계·검증) | MCP 리서치, 브라우저 실측, 프로덕션 검증, 배포 확인, 문서 갱신, DB 실측 조회 | 코드 파일 생성/편집, `git commit`/`push` | PRD·설계문서, 시즌/카테고리 리서치, dry-run 결과 검증, 트래커 rev 기입 |
| **Code** (구현·배포) | 코드 작성·편집, 커밋, 빌드/tsc, 테스트, 대용량 한글 MD 전체 덮어쓰기 | 브라우저 실사용 검증(육안), 운영자 승인 대체 | 라우트/라이브러리 구현, 순수함수 단위검증, `verify-vercel-deploy` |
| **Cowork** (문서·리서치) | 여러 파일에 걸친 광범위 리서치·문서 정리·정정, 로컬 파일 커밋 | 코드 파일 수정(레인 충돌 시 금지), 운영자 승인 대체 | 문서 정합성 정정, 공백 채움, 크로스 문서 감사 |

> **레인 선택 기준**: 파일 3개 이하 코드 작업은 Code 단독이 효율적. 여러 파일 걸친 문서 정리·리서치는 Cowork. 실측·검증·설계는 Desktop.

## 2. write set 규약 (병렬 안전의 유일한 기준)

**write set** = 그 작업이 *수정하는* 파일 목록. 두 작업의 write set이 겹치지 않으면 병렬 안전(wikidocs 098·원칙 #322).

- 병렬 판단은 **주제 유사성이 아니라 write set 겹침 여부로만** 한다(#322). "둘 다 소싱 작업"이어도 파일이 다르면 병렬 안전.
- **담당 write set 밖의 파일은 되돌리거나 정리하지 말 것**(wikidocs 097). 범위 밖 변경을 발견하면 **수정하지 말고 요약만** 남긴다.
- 착수 전 자기 write set을 인계 메시지에 명시한다. 상대 레인이 겹치는 파일을 잡고 있으면 순차로 전환.

**모범 사례(rev112/rev113)**: `wholesale-matcher.ts`(Code) ↔ `SourcingRecommendWidget.tsx`(Desktop) write set 분리로 트랙③ 1·2단계 병렬 무충돌.

## 3. 핑퐁 인계 형식 (레인 → 레인 전달)

한 레인이 다음 레인으로 넘길 때 **채팅 본문 + 인계문서** 둘 다 남긴다.

### 3-A. 채팅 핵심 인계 메시지 (매 턴 마무리 필수)
```
[완료]   이번 턴에 실제로 끝낸 것(검증 근거 = 파일:라인 or 쿼리결과 or 커밋해시)
[미진행] 착수했으나 못 끝낸 것 + 막힌 이유
[다음]   다음 레인이 이어서 할 일 (담당 레인 명시)
[병렬]   의존성 없이 지금 동시에 해도 되는 작업 (write set 명시)
```

### 3-B. 인계문서 (트랙 단위, `docs/handoff/`)
- 지시: `CODE_<트랙>_HANDOFF_<date>.md` (Desktop→Code 배분)
- 결과: `CODE_<트랙>_RESULT_<date>.md` 또는 `_<date>.md` (Code→Desktop 보고)
- 세션 전체 현재상태: `docs/handoff/CURRENT.md` (다음 세션 진입점·항상 최신)

### 3-C. rev 기입 권위
- **트래커 rev 추가·번호 부여는 원칙적으로 Code 레인**(대용량 MD 처리 권한). 다른 레인은 rev를 임의로 추가하지 않는다(충돌 방지).
- `PARALLEL_WORK_TRACKER.md` 최신 rev = 프로젝트 현재 상태의 단일 권위. `PROGRESS.md`는 그 요약 로그.

## 4. 절대 금지 (전 레인 공통, 매 턴 확인)

- 네이버 스토어 PUT/POST(비가역 쓰기) → 운영자 명시 "GO" 없이 금지.
- 디스코드 실발송(크론 수동 실행) → 운영자 승인 없이 금지(실제 알림이 나감).
- 매일 자동 실발송을 일으키는 CI 워크플로(GitHub Actions 등) 추가·활성화 = 디스코드 실발송 동급 승인 대상.
- 테스트 데이터 방치 → 주입했으면 같은 세션에 원복.
- 허위 완료 보고 → 실측 못 한 건 "미검증" 명시(#310). 인계문서의 "확인됨/완료" 서술도 재검증 대상.
- 다른 레인 동시 작업 중 → 담당 write set 밖 파일 손대지 말 것.

## 5. 커넥터 이중화 (읽기·쓰기 경로가 막히면)

Filesystem MCP ↔ Desktop Commander ↔ iterm ↔ Chrome은 상호 백업이다(#298). 하나가 죽어도 다른 것으로 읽기·쓰기·검증 가능. 4분 행(#26) 패턴은 재시도 말고 즉시 다른 커넥터로 전환. 전수 시도 전에 "못 한다"고 보고하지 않되, 전부 실패하면 지어내지 말고 사실대로 보고.
