# AI 협업 문서 관리 표준 리서치 (2026-07-24)

> 상태: 시점(2026-07-24) · 리서치 원본 요약
> 한 줄 요약 — Claude와 협업할 때 문서가 많아지면 왜 성능이 떨어지는지, 어떻게 정리해야 하는지.
> 적용 결과는 `docs/DOCS_STANDARD.md`(영구)에 반영됨. 이 문서는 근거 보관용.

## 0. 핵심 결론 3줄

1. **문서가 많으면 Claude가 더 똑똑해지는 게 아니라 더 멍청해진다.** 읽지 않은 낡은 문서도 맥락에 섞이면 성능을 깎는다.
2. **CLAUDE.md는 200줄 이하가 공식 권고.** 우리는 현재 **346줄** — 초과 상태.
3. **인계 문서는 "항상 1개"만 살아있어야 한다.** 우리는 **107개** 누적 — 어느 게 최신인지 Claude가 판단 불가.

## 1. Anthropic 공식 권고 (근거 있는 사실)

| 항목 | 공식 내용 |
|---|---|
| CLAUDE.md 크기 | **"200줄 이하를 목표로"**. 길수록 맥락을 잡아먹고 **지시 준수율이 떨어진다** |
| 무엇을 넣나 | Claude가 추측할 수 없는 것만 — 빌드/테스트 명령, 비표준 관례, 프로젝트 고유 결정, 함정 |

## 2. "맥락 부패(Context Rot)" — 실험으로 증명된 현상

**Chroma 기술 보고서**(2025년 7월, Kelly Hong·Anton Troynikov·Jeff Huber)
- **18개 최신 모델**(GPT-4.1, Claude 4 Opus/Sonnet, Gemini 2.5, Qwen3 등)에 **194,480회 호출** 실험.
- 결론: **"모델은 맥락을 균일하게 쓰지 않는다. 입력이 길어질수록 성능이 점점 불안정해진다."** 아주 단순한 과제에서도 그렇다.
- 충격적 결과: **집중된 300토큰 프롬프트가 전체 113,000토큰 프롬프트보다 모든 항목에서 더 좋았다.** Claude 계열에서 그 격차가 **가장 컸다**.
- 또 하나: 논리적으로 잘 정리된 자료 더미가 **뒤죽박죽 섞은 것보다 오히려 성능이 나빴다**.
- **"N토큰 넘으면 나빠진다"는 절벽은 없다.** 처음부터 조금씩 계속 나빠진다.

**"색인병(Index Sickness)" 사례연구**(2026, arXiv 2606.19121 · 391회 연속 세션)
- AI가 스스로 관리한 문서·기호 체계가 오히려 성능을 떨어뜨리는 현상.
- **공간적**: 기호가 너무 많아 주의가 분산되고 "다 안다는 착각"이 생김.
- **시간적**: 격리되지 않은 과거 기록이 새 작업의 의미 공간을 **오염**시킴.
- 핵심 명제: **"기호가 많을수록 AI는 덜 이해한다."**
- 원인: 어텐션은 **기호의 '유효 여부'를 구분하지 못한다** — 일단 맥락에 들어오면 그 내용이 이미 폐기됐든 말든 계속 작동에 관여한다.
- 처방: 형식화된 기호보다 **자연어**를, 그리고 보관 문서는 **물리적으로 격리**할 것.
- ⚠️ 한계: AI가 자기 자신을 관찰한 1건짜리 사례연구. 방향은 참고하되 수치는 검증되지 않음.

**커뮤니티 통설**(공식 아님)
- 최신 모델이 안정적으로 따르는 지시 개수 ≈ **150~200개**. Claude Code 시스템 프롬프트가 이미 ~50개를 씀.
- 200줄 CLAUDE.md ≈ 1,500~2,000토큰. 6개월 된 실제 프로젝트는 흔히 **800~1,500줄로 비대해짐**.

## 3. 여러 세션이 한 저장소를 다룰 때 (우리 상황과 직결)

**Anthropic "장기 실행 에이전트를 위한 효과적 하네스"**(2025-11-26) — 가장 권위 있는 패턴
- 세션 간 기억 상실 문제를 이렇게 푼다:
  - **초기화 에이전트**가 환경을 한 번 세팅하고, 사용자 요청을 구조화된 **`feature_list.json`**으로 펼침.
  - **작업 에이전트**를 반복 호출 — "기능 하나를 조금 전진시키고, 테스트 돌리고, **`claude-progress.txt`에 메모 남기고, 커밋**하라".
- **결정적 선택**: 상태 파일을 **JSON으로 썼다.** 이유는 **"모델이 Markdown보다 JSON을 함부로 바꾸거나 덮어쓸 가능성이 낮기 때문"**. 수정도 `passes` 불리언만 뒤집게 제한.
- 이름 붙인 실패 유형: **성급한 승리 선언** · 버그 있는 상태로 방치 · **끝까지 테스트 안 하고 완료 표시**.

**실무자들이 수렴한 인계 규칙**
- 브랜치/주제당 **활성 인계는 1개**만.
- 인계 문서 머리에 `status` · `branch` · `goal` · `next-action`.
- **받는 쪽은 인계문을 믿지 말고 저장소 현재 상태와 대조 검증**해야 한다 — *"현재 저장소가 진실의 원천"*, *"문제는 기억이 없는 게 아니라 검증되지 않은 기억이다."*
- 낡은 인계는 **즉시 보관 처리**하거나 표시해야 한다.
- 인계를 통째로 다음 세션에 쏟아붓는 건 **"자동요약에 절차만 더한 것"**. 산문 덩어리가 아니라 **구조화된 상태**를 넘겨야 한다.

| 프레임워크 | 판정 | 이유 |
|---|---|---|
| **Diátaxis**(튜토리얼/방법/참조/설명) | ✅ **부분 채택** | 문서 종류를 섞지 않게 하는 **분류 렌즈**로 유용. 4분면 상호링크 규율까지는 불필요 |

## 5. 이커머스/백오피스 특화

- **상태 머신**(commercetools 권고): `State1` 같은 이름 금지. `OrderCreated`·`PaymentAuthorized`처럼 서술적으로. **"모든 전이가 가능해 보여도 전이를 명시적으로 정의하라 — 데이터 무결성을 강제하고 잘못된 상태 변경을 막는다."** 산문이 아니라 **전이 표**로 기록.
- **런북**: 설명서가 아니라 **행동 지시서**. *"전략 아키텍처 문서도, 1회성 장애 보고서도 아니다 — 실행 가능하고, 관측 가능하고, 버전 관리돼야 한다."* 이름은 **서비스 + 문제 유형**("네이버 동기화 연결 고갈"). 구조: 목적 → **발동 조건** → 단계별(기대 결과·분기) → 검증 → 롤백. 진단용과 복구용을 분리.

## 6. 출처가 엇갈리는 지점 (주의)

| 쟁점 | 상황 |
|---|---|
| import 깊이 | 현행 문서는 **4단계**, 구 문서·3자 가이드는 **5단계**. 깊은 체인 자체를 피하는 게 안전 |
| 200줄 | **절벽이 아니라 권고**. 201줄에서 갑자기 망가지는 게 아님 |
| CLAUDE.md vs AGENTS.md | Claude만 쓰면 CLAUDE.md 단독이 정답. 다른 AI 도구를 병행할 때만 AGENTS.md 도입 |
| Markdown vs JSON | **기계가 갱신하는 상태 파일**은 JSON이 안전(덮어쓰기 위험 낮음) |
