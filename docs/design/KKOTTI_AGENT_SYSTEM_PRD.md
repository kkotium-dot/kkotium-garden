## 0. ★ 가장 중요한 전제 — "에이전트"는 3가지 계층이다 (#321)

운영자와 개발 레인이 같은 단어를 다르게 이해하면 몇 주를 낭비한다. 이 프로젝트에서 "에이전트"는 아래 3개 중 하나를 정확히 가리켜야 한다.

| 계층 | 정체 | 위치 | 언제 도는가 | 아침 8시 디스코드 발송 |
|---|---|---|---|---|
| **A. Claude Code 서브에이전트** | 개발 보조 AI | `.claude/agents/*.md` | 운영자가 Claude Code를 켜고 작업할 때만 | ❌ 불가능 |
| **B. Desktop MCP 도구** | 리서치·검증 AI (지금 이 세션) | Claude Desktop | 운영자가 대화할 때만 | ❌ 불가능 |
| **C. 앱 내부 파이프라인** | 프로덕션 코드 | `src/lib/` + Vercel Cron | **24시간 자동** | ✅ 가능 |

**운영자가 원하는 "내 일을 대신하는 에이전트"는 C다.** A와 B는 C를 *만드는* 도구일 뿐, C를 *대체하지 못한다*.
- A는 이 PRD의 §7(구현 보조)에서만 사용.
- B는 이 PRD의 §5(시즌 캘린더 데이터 구축)에서 1회성으로 사용.
- **C가 본 PRD의 본체다.**

## 1. 배경

**현재 문제 (2026-07-30 실측 확정)**:
- `/api/cron/daily` (매일 08:00 KST)가 `computeRecommendation(products)`를 호출 — `products`는 **자사 DB에 이미 있는 상품**뿐이다. 그래서 매일 "이미 크롤링한 것" 중에서만 순위를 바꿔 추천한다. 운영자가 체감한 "제대로 안 온다"의 정확한 원인.
- 반면 **신규 발굴 엔진은 이미 존재한다**: `src/lib/sourcing-recommender.ts`(496줄)가 DataLab 트렌드 → 검색량 → 경쟁분석 → 도매꾹/도매매 OpenAPI 실시간 검색 → 마진계산 → 황금🏆/니치💎/시즌🗓️ 태그까지 수행. **그런데 어떤 크론에도 연결돼 있지 않다**(`vercel.json` crons에 `/api/sourcing-recommend` 없음). 수동 POST 아니면 절대 실행되지 않는다.
- 좀비·품절·마진위기·발행준비 알림은 이미 정상 작동 중(`computeOpsDigestSignals`).

**왜 지금인가**: 새싹셀러 단계에서 "무엇을 팔지 고르는 시간"이 가장 큰 병목이다. 이 판단을 앱이 대신 해주고 운영자는 컨펌만 하면, 하루 1~2시간을 상품 발굴이 아닌 상세페이지 품질에 쓸 수 있다.

## 2. 목표

- **운영자가 할 일**: 아침에 디스코드 알림 하나 열고 → 후보 카드 보고 → 채택/보류 누르기. 그게 전부.
- **시스템이 할 일**: 트렌드 수집 → 도매처 실물 매칭 → 마진·경쟁 검증 → 오류 걸러내기 → 알림 + 앱 대기열 등록.
- **기대 효과**: 상품 발굴 소요시간 감소, 시즌 선점(리드타임 확보), 니치 키워드 진입으로 초기 노출 확보.

- ❌ 자동 발주/결제 — 범위 밖.
- ❌ 다중 셀러·권한등급 — 미사용 개념.
- ❌ Claude Code 서브에이전트가 프로덕션에서 도는 구조 — 기술적으로 불가능(§0 참조).

## 5. 시스템 설계 — 꼬띠 에이전트 팀 (앱 내부, 계층 C)

기존 코드를 **역할이 보이는 파이프라인**으로 재구성한다. 새로 만드는 게 아니라 있는 걸 연결 + 검수관 신설.

| # | 역할 | 하는 일 | 현재 상태 |
|---|---|---|---|
| 1 | 🔍 **정찰병**(Scout) | DataLab 트렌드 · 검색량 · 경쟁도 · 도매 플랫폼 실시간 검색 | **이미 있음** `sourcing-recommender.ts` |
| 2 | 🧠 **전략가**(Strategist) | 시즌/니치/황금 판정 · 마진 계산 · 진입장벽 평가 | **이미 있음** (블루오션 점수·recoType) |
| 3 | ✅ **검수관**(Inspector) | 품절·마진미달·중복·금지카테고리 자동 배제 + 근거 기록 | **신설 필요** ← P3 |
| 4 | 📢 **전령**(Herald) | 디스코드 발송 + 앱 개입 대기열 등록 | **이미 있음** `sendDiscord` |

**핵심 설계 원칙**: 4역할은 **순수 함수 모듈**로 분리한다. 각 역할의 입력/출력이 명확해야 개별 테스트와 dry-run이 가능하다(#98 write-set 분리 원칙의 코드 버전).

### 5-1. 웹 데이터 수집 범위 — 정직한 한계 (중요)

운영자가 "MCP로 더 깊고 넓게"를 요청 — **부분적으로 가능하지만 계층을 구분해야 한다**:

| 데이터 | 수집 방법 | 프로덕션 자동화 | 비고 |
|---|---|---|---|
| 검색 트렌드·검색량 | 네이버 DataLab / 검색광고 API | ✅ 가능 | 공식 API, 이미 구현됨 |
| 경쟁 상품·가격대 | 네이버 쇼핑검색 API | ✅ 가능 | 공식 API, 이미 구현됨 |
| 도매 상품 실물 | 도매꾹 OpenAPI | ✅ 가능 | 공식 API, 이미 구현됨 |
| **시즌·이슈 캘린더** | **Desktop MCP 리서치(1회성)** | ⚠️ **반자동** | 아래 참조 |
| 임의 웹사이트 스크래핑 | — | ❌ **하지 않음** | ToS 위반·차단 위험 |

**시즌 캘린더의 올바른 방식(계층 B 활용)**: Desktop(이 세션)이 MCP로 한국 커머스 시즌·이슈를 리서치해 **풍부한 시드 데이터셋**(`src/lib/season/season-calendar.ts`)을 구축 → 앱은 그 데이터셋 + 실시간 DataLab을 조합해 매일 판단. 즉 **MCP는 "연구·데이터 구축", 앱은 "매일 실행"**. 이게 MCP를 가장 크게 활용하는 현실적인 방법이다.

현행 `getSeasonContext()`는 6개(발렌타인/화이트/어린이/어버이/빼빼로/크리스마스)뿐 — **설·추석·신학기·장마·김장·블프·이사철·여름가전·겨울가전 등이 전부 누락**. 이것이 "시즌 전략 상품"이 안 나오는 직접 원인.

## 6. 기능 요구사항

- **FR-1** 매일 정해진 시각, 신규 소싱 후보를 자동 생성해 디스코드 `KKOTTI_RECOMMEND` 채널로 발송한다.
- **FR-2** 후보 각각에 **근거**를 함께 표시한다: 검색량, 경쟁강도, 예상마진, 도매처명·공급가, 시즌 리드타임.
- **FR-3** 검수관이 배제한 항목은 **배제 사유와 함께 카운트만** 보고한다(조용히 사라지지 않음 — #283 침묵 제외 금지 원칙 재사용).
- **FR-4** dry-run 모드에서 디스코드 발송 없이 동일 결과를 JSON으로 확인할 수 있다.
- **FR-5** 시즌 캘린더는 이벤트별 **리드타임**(예: 크리스마스는 D-45부터 소싱 시작)을 갖는다.
- **FR-6** 후보는 앱 「꼬띠 브리핑」 화면에도 동일하게 나타나며, 운영자가 채택/보류를 누를 수 있다.
- **FR-7** 채택된 후보는 기존 소싱 흐름(꿀통 꽃나들이)으로 자연스럽게 이어진다 — 별도 우회 경로를 만들지 않는다(#56 개입 자연스러움).

## 7. 비기능 요구사항

- **성능**: 크론 1회 실행이 Vercel 함수 타임아웃 내에 끝나야 한다. 외부 API 호출이 많으므로 **키워드 수 상한**과 **부분 실패 허용**(한 키워드 실패가 전체를 죽이지 않음) 설계 필수.
- **보안**: 도매꾹 API 키는 `store_settings` DB에서만 읽는다(이미 그렇게 구현됨). 로그에 키 값 출력 금지.
- **비가역성**: 이 시스템은 **읽기 전용**이다. 네이버 PUT/POST 절대 없음. 디스코드 발송만 외부 부작용이며 dry-run으로 차단 가능.
- **정직성**: 데이터를 못 가져왔으면 "못 가져왔다"고 표시한다. 추정치를 확정 사실처럼 쓰지 않는다(#46 거짓 라벨 금지).

## 8. 수용 기준

- [ ] Given 크론이 실행될 때, When 신규 소싱 후보가 1건 이상 생성되면, Then 디스코드에 근거(검색량·마진·도매처)가 포함된 카드가 발송된다.
- [ ] Given 후보가 0건일 때, When 크론이 끝나면, Then "오늘은 조건에 맞는 후보가 없어요"가 명시적으로 발송된다(침묵 금지, #257 선례 재사용).
- [ ] Given dry-run 파라미터가 켜졌을 때, When 크론/API를 호출하면, Then 디스코드 발송 없이 동일 결과 JSON만 반환된다.
- [ ] Given 검수관이 후보를 배제했을 때, When 결과를 확인하면, Then 배제 건수와 사유별 분류가 함께 보인다.
- [ ] Given 시즌 이벤트가 리드타임 내에 있을 때, When 후보를 생성하면, Then 해당 시즌 키워드가 우선 반영된다.
- [ ] Given 운영자가 앱에서 후보를 채택할 때, When 채택 버튼을 누르면, Then 기존 소싱 흐름으로 연결되고 채택 이력이 기록된다.

## 9. 검증 계획

- **dry-run 우선**: 실제 디스코드 발송 전에 반드시 dry-run으로 결과 확인 → 운영자 승인 → 실발송 활성화. (프로젝트 절대금지: 디스코드 실발송은 운영자 승인 없이 금지)
- **단위**: 검수관 필터 로직은 순수 함수로 테스트(입력 후보 배열 → 통과/배제 결과).
- **통합**: 로컬 dev에서 dry-run API 호출 → JSON 구조 검증.
- **브라우저**: 「꼬띠 브리핑」 화면 실제 렌더 확인(#63 실사용 브라우저 테스트 통과 후 다음 작업).
- **외부 API**: DataLab·쇼핑검색·도매꾹 응답을 실측으로 검증(#181 verify-first, 스펙 문서 맹신 금지).

## 11. 구현 순서 (의존성 그래프)

```

  │   write set: vercel.json, src/app/api/cron/daily/route.ts,
  │              src/app/api/sourcing-recommend/route.ts
  │
  ├─▶ [P3] 검수관 신설 (필터 + 배제사유 기록)   ← P1의 출력이 있어야 필터 대상이 생김
  │      write set: src/lib/sourcing/inspector.ts (신규)
  │
  └─▶ [P4] 앱 「꼬띠 브리핑」 화면              ← P3 완료 후(배제사유까지 보여줘야 함)

              │
              └─▶ [P5] 피드백 루프              ← P4 필요(채택 버튼이 있어야 데이터가 쌓임)

       write set: src/lib/season/season-calendar.ts (신규), src/lib/discord.ts(getSeasonContext 교체)
```

wikidocs 092/097/098 검토 결과, **이 프로젝트에 도입할 가치가 있으나 우선순위는 낮다**.
