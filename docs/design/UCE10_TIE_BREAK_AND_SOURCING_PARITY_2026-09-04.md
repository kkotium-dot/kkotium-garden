## A. 소싱 파이프라인 검증경로 우회

### 실측 근거
- DB(`sourcing_opportunity_records`, 2026-09-02~09-03 레코드): "거실LED등"·
  "입간판"·"거실등"·"무드등"·"배너" 5건이 `"식품(카테고리 미확정)"` 라벨로
  저장됨(생활잡화·조명·디지털 상품인데 "식품"이 붙음 — trendD1 폴백 문자열이
  그대로 노출된 것).
- Vercel 런타임 로그(`/api/category/suggest`, 15분 윈도우) 실측: 같은
  키워드를 API route에 태우면 Groq이 "거실등"→`가구/인테리어>조명>거실등`,
  "무드등"→`가구/인테리어>조명>무드등` 등 유효 후보를 만들어낸다(로그 원문
  `[category/suggest][groq-raw]` 태그로 확인).
- 코드 확인(`src/lib/sourcing-recommender.ts` L601): 소싱 파이프라인은
  ```ts
  const ucMatch = matchDeterministicCategories(kw.keyword)[0];
  const matchedCat = ucMatch ? ucMatch.d1 : `${trendD1}(카테고리 미확정)`;
  ```
  — `matchDeterministicCategories()` **단독** 호출. `isDeterministicLowConfidence`
  게이트도, Groq 교차확인도, `validateSuggestion()`(마스터 실재 검증)도 거치지
  않는다. `/api/category/suggest`(씨앗심기 UI가 쓰는 정식 3단 경로)와 완전히
  다른 코드 경로다.

### 왜 문제인가
원칙 #295(단일 권위) 위반 — 같은 "카테고리 판정"이라는 문제에 검증 수준이

노출되는 사용자 대면 정보인데, 씨앗심기보다 낮은 신뢰도로 만들어지고 있었다.

## B. "~용~" 삽입 정규화 부재

### 실측 근거
- 마스터 전수 스캔: `d4||d3` 리프명에 "용"이 포함된 항목 355건.
- "용" 제거 정규화 시 서로 다른 브랜치가 충돌하는 쌍: **3건뿐**(기타튜닝용품
  PC/자동차, 눈귀관리용품 강아지/고양이, 미용가위 반려동물/헤어)이며 셋 다
  주변 문맥(다른 명사)으로 이미 구분 가능 — 정규화가 새 오분류를 만들
  위험은 낮다.
- 재현: "실내방향제"(상품명 관용 표기) vs 마스터 리프 "실내**용**방향제"
  (공식 카테고리명) — 순수 substring 불일치로 매처가 완전히 다른 리프
  (`스포츠/레저>캠핑>랜턴>실내/실외등`, "실내" 부분매칭)로 새어나갔다.
  "차량방향제" vs "차량**용**방향제"도 동일 패턴(이쪽은 d2까지는 맞았으나
  d4까지 못 감).
- 시뮬레이션 검증(`haystacksNorm = haystacks.map(stripYong)`로 leaf도
  같이 정규화해 재비교): "실내방향제"→`생활/건강>생활용품>제습/방향/탈취>
  실내용방향제`, "차량방향제"→`생활/건강>자동차용품>공기청정용품>
  차량용방향제` — 둘 다 정확한 d4까지 잡힘. 회귀(기존 정답 케이스: 빨래건조대·
  무선청소기·요가매트·달항아리·아이스트레이·수세미)는 실제 매처가 이미
  tier/스코어링으로 처리 중이라 이 정규화 자체와는 무관 — 깨지지 않음.

### 참고: 별건 — "레일조명"·"도어스토퍼"는 정규화로 해결 안 됨
두 케이스는 마스터에 해당 정확 리프가 아예 없는 **커버리지 공백**이다
(레일조명은 인테리어조명류로 뭉뚱그려짐, 도어스토퍼는 도어벨/도어락/
도어스커프만 있고 정확 대응 리프 없음). 이건 매처가 아니라 마스터 자체의
공백이라 이번 수정 범위 밖 — UCE-4 개입큐(사람 확인)로 흘러가는 게 맞는
경로이며, 실제로 그렇게 되는지는 §D에서 확인한다.

## C. isLeafItself 동점보너스 — 구조적 오분류 (핵심 발견)

### 근본 원인
`category-deterministic-matcher.ts` L228-232:
```ts
const isLeafItself = !c.d4;
if (c.d3 && c.d3 === headNoun) {
  consider(`${c.d1}|${c.d2}|${c.d3}`, {
    ...
    score: c.d3.length * EXACT_BRANCH_SCORE_PER_CHAR + (isLeafItself ? 1 : 0),
  });
}
```
헤드노운이 d3 브랜치명과 정확히 일치할 때, "그 d3 자체가 이미 리프(자식
d4 없음)"인 경우 +1점을 더한다. 원 의도(UCE-9 주석)는 "ancestor 라벨보다
실제 판매단위(leaf)를 우선"이었으나, 부작용으로 **"우연히 이름이 같고
자식이 0개인 마이너 카테고리"가 "자식을 여러 개 가진 진짜 주력
브랜치"를 상시 이기게** 만든다.

### 전수 스캔 결과 (원칙 #352 절차)

"자기자신이 리프"인 쌍을 전수 스캔 → **16건** 발견:

### 재현 확인 (실제 함수 호출)
`matchDeterministicCategories()`로 11개 표본 실행 — **전건 1순위가 왼쪽
(틀린 쪽)**:
```
우산 -> 출산/육아>유아동잡화>우산[t1,61.0] (2위: 패션잡화>패션소품>우산[60.0])
스카프 -> 출산/육아>유아동잡화>스카프[91.0] (2위: 패션잡화>패션소품>스카프[90.0])
소파 -> 가구/인테리어>아동/주니어가구>소파[61.0] (2위: 거실가구>소파[60.0])
조명 -> 생활/건강>관상어용품>조명[61.0] (2위: 인테리어소품>조명[60.0])
... (11/11 동일 패턴)
```
1점 차이로 매번 틀린 쪽이 이긴다 — 명백한 설계 결함이지 우연이 아니다.

### 수정안 검증 (dryRun 시뮬레이션)
`isLeafItself ? +1 : 0`을 **"형제 d4 개수가 많을수록 근소 가산"**으로
대체(로그스케일로 과도한 쏠림 방지, `Math.min(2, Math.log2(childCount+1)*0.5)`):
- 11/11 케이스 전부 정답(자식 많은 진짜 브랜치)으로 승자 교체 확인.
- "유아소파"·"유아책상" 같은 **진짜 유아용 복합명사**는 이미 tier1 완전
  리프매칭(compound noun, 121점)으로 이 동점 로직과 무관하게 압도적으로
  이기므로 회귀 없음(검증 완료).
- 참고로 "아기우산"·"아기의자"(수식어+헤드노운 조합, 복합명사 사전에
  미등재)는 **현재도 여전히 부정확**(별개 결함 — 수식어 인식 자체가 약함,
  이번 스코프 밖으로 UCE-11 후보로 기록만 함).

## D. UCE-4 개입큐가 실제로 작동하는지 (레일조명·도어스토퍼류 안전망)

**실측(DB + 코드 배선 확인)**: `internalTags`에 `category_confirm_needed`가
걸린 상품 **0건**(`Product` 테이블 전체). 배선 자체는 실재한다
(`api/category/suggest/route.ts` → `updateCategoryConfirmFlag` →
`UploadReadinessWidget.tsx` L362가 렌더) — 죽은 코드는 아니다.

**그러나 이 0건이 "안전"을 의미하지 않는다(#350, 표면신호 재검증 원칙).**
플래그는 `suggestions.length === 0`(결정론+AI **둘 다** 완전 실패)일 때만
걸린다. §C에서 확인했듯 "우산"·"소파"·"조명" 같은 동점충돌 케이스는
결정론이 **뭔가는(오답이라도) 반환**하므로 이 게이트를 그냥 통과해
사람 확인 없이 저장된다 — 즉 개입큐는 "완전 빈손"만 잡고 "확신에 찬
오답"은 못 잡는다. §C 수정이 이 개입큐보다 우선순위가 높은 이유이기도
하다 — 애초에 동점에서 정답이 이기면 개입큐로 보낼 필요조차 없어진다.
