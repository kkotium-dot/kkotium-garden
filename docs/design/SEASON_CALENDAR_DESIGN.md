## 1. 음력 처리 방식 (결함 #3 — 가장 치명적)

현행 `{month, day}` 구조는 음력을 못 담는다. 3가지 옵션:

| 옵션 | 방식 | 장점 | 단점 | 권장 |
|---|---|---|---|---|
| A. 환산 테이블 | 연도별 양력 환산일을 데이터에 하드코딩(`date:{2026,2027,2028}`) | 의존성 0·정확·검증 완료 | 매년(또는 3년마다) 표 갱신 필요 | ★ **채택** |
| B. 음력 계산 라이브러리 | `lunar-javascript` 등 런타임 변환 | 자동·영구 | 의존성 추가·검증 부담·번들 증가 | 보류 |
| C. 외부 API | 공휴일 API 호출 | 항상 최신 | 네트워크 의존·장애점·1인운영 과함 | 미채택 |

### 권장: 옵션 A (환산 테이블)
- 데이터에 이미 2026~2028 환산일 확정(다중소스 검증·전부 high).
- `type: 'lunar'`이면 `date[currentYear]`를 룩업. **표에 없는 연도 = fail-safe**로 "환산일 미확보(재검토)" 로그 후 스킵(추측 금지 #303).
- **갱신 규칙**: 매년 12월 다음 3년치 환산일을 표에 append(연 1회 유지비 최소).
- 근거: 이 앱은 소싱 추천용이라 "정확한 D-day"가 핵심이고, 라이브러리 오차·번들 비용보다 **검증된 하드코딩 3년치**가 안전(COLLABORATION_PLAYBOOK #1 기존방식 우선).

### 의사 로직 (Code 참고용 · 구현 아님)
```
resolveDate(event, year):
  if event.type == 'solar':  return {year, event.date.month, event.date.day}
  if event.type == 'lunar':  return event.date[year] ?? null   // null이면 스킵+로그
  if event.type == 'range':  return {start, end}                // 구간 판정
```

## 2. 겹침 처리 방식 (결함 #4 — 첫 매치만 반환)

현행은 매치 1건에서 멈춘다. 5월(어린이날+어버이날+스승의날), 11월(빼빼로+광군제+김장+블프+가전) 등 **다중 겹침**이 흔하다.

### 권장: 전체 수집 → 우선순위 정렬 → 상위 N 반환
```
active = 모든 이벤트 중 (오늘이 리드타임 창 안 or range 구간 안)인 것 전부
정렬 키:
  1) 임박도 = daysLeft 오름차순 (가까운 것 먼저)
  2) 동률이면 leadTimeDays 큰 것 먼저 (준비 오래 걸리는 것 우선 경고)
return active.slice(0, N)   // 알림은 상위 2~3, 소싱엔진은 전체
```
- **반환 타입 변경**: 현행 `단일 | null` → **배열**. Code가 시그니처 조정(소비처 영향 확인 필요 — Code 담당).
- **소비처별 상한**: 디스코드 알림 = 상위 2건(피로 방지 #300 계열), 소싱 엔진 = 전체(누락 방지).
- range와 solar가 섞여도 동일 정렬(range는 daysLeft = 구간 시작까지, 이미 구간 안이면 0).

## 3. 리드타임 계산식 (결함 #2 — 30일 고정)

이벤트마다 소싱 준비 기간이 다르다(크리스마스 트리 D-55 vs 스승의날 소품 D-25).

### 판정식
```
daysLeft = resolveDate(event, year) - today   // solar/lunar=당일, range=구간 시작
isActive =
  event.type == 'range'
    ? (today ∈ [start, end])  OR  (0 <= (start - today) <= leadTimeDays)
    : (0 <= daysLeft <= event.leadTimeDays)
```
- **리드타임 창**: `D-leadTimeDays ~ D-day`. 이 안에 들면 "소싱 착수 시기".
- **피크 창**: `D-peakWindowDays ~ D-day`. 판매 집중 구간(알림 톤 강화용).
- 두 창 분리 이유: 소싱은 일찍 시작(리드타임), 판매 강조는 임박 시(피크). 상태축↔권고축 분리(#300)와 같은 사상.

### leadTimeDays 부여 근거 (데이터 파일)
| 이벤트군 | 리드타임 | 근거 |
|---|---|---|
| 크리스마스·명절 | 45~55 | 트리·명절선물 재고 조기 소진, 드롭십 셀렉트+발행 여유 |
| 계절가전(여름/겨울) | 35~40 | 성수기 전 재고 확보, 피크 길다 |
| 기념일 소품 | 25~35 | 포장·소품은 회전 빠름 |
| 쇼핑 이벤트 | 35~40 | 특가 물량 사전 확보 |

## 4. 취급 제외 필터 (운영자 정책 · 상시)

데이터 단계에서 이미 식품·화장품·브랜드 키워드를 배제했으나, **소싱 엔진에도 방어선**을 둔다:
- 시드 키워드가 DataLab에서 식품·화장품 카테고리로 확장되면 그 결과를 **드롭**(카테고리 화이트리스트 = 생활/주방/인테리어/디지털/스포츠레저/출산육아).
- 이 필터는 Code가 소싱 엔진에 구현(본 설계는 명시만).

## 5. 연도 롤오버 (경계)
- 혹한기(12/15~2/10)·연말선물처럼 **연 경계를 넘는 range**는 시작연도 기준으로 두 구간(작년12월+올해1~2월) 판정.
- 음력 표는 매년 12월 3년치 append. 표 없는 연도는 스킵+로그(fail-safe, 추측 금지).
