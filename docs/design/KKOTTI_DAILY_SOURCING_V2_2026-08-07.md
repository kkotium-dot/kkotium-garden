> 상태: **설계 확정**(2026-08-07 Desktop). 운영자 방향 확정 반영 + 도매매 API 실측 근거.
> 한 줄 요약 — 트렌드 신호(세상이 원하는 것)를 **보여주면서**, 그 신호로 **내 공급사 안에서 실제 뗄 수 있는 최적 상품을 매칭**해 매일 아침 10개 추천. 디스코드=모바일 요약, 앱=상세 완결. 품절 대체상품 축 연계.

## 0. 문제 정의 (운영자 방향)

기존 소싱 추천은 **"트렌드 키워드 → 도매 검색"** 한 방향이다. 운영자 요청:
1. **트렌드 정보도 알려주면서** — 세상이 뜨는 신호(검색량·경쟁·블루오션)를 계속 제공하되,
2. **공급사 기준 최적 상품도 추천** — 내가 실제 거래하는 공급사(도매매 셀러) 안에서 그 트렌드에 맞는 상품을 매칭.
3. **품절 대체상품** 등 확장 아이디어.

핵심: 두 축을 **분리 나열이 아니라 결합**한다 — "트렌드 신호 × 공급사 상품 = 내가 지금 뗄 수 있는 검증된 기회".

## 2. ★ 실현 가능성 실측 — 공급사 축 (도매매 API 공식 문서)

**도매매 OpenAPI v4.1 getItemList는 `id`(판매자 아이디) 파라미터를 지원한다**(공식 레퍼런스 확인, 2026-08-07):
> "상품목록 검색을 위하여 아래 검색 조건 중 하나 이상의 파라미터 설정이 필요합니다. 기획전번호(ev), 카테고리(ca), **아이디(id)**, 검색어(kw), 상품번호(itemNo)"

- 즉 `getItemList?id={domeggookSellerId}&ca={카테고리}` 조합으로 **특정 공급사의 특정 카테고리 상품**을 조회 가능.
- 응답에 `categoryId`·`categoryName`·`sellerLv`(셀러 등급)·`price`·`unitQty` 포함.
- **판매중인 상품만 반환**(판매중지·종료·품절·단종 제외) → 항상 살아있는 상품. 품절 대체 축에도 유리.
- 우리 `Supplier.domeggookSellerId`(이미 존재)와 직결 → **인프라 절반 이미 있음**.

→ 공급사 축 B는 **새 API가 아니라 기존 `searchDomeggookMarket()`에 `id` 파라미터 추가**로 구현 가능. 난이도 낮음.

## 3. ★ 개선 설계 — 트렌드 × 공급사 결합

### 3-1. 통합 소싱 파이프라인 (3-소스 → 통합 스코어 → 10개 엄선)

```
[트렌드 축]    네이버 트렌드/키워드 → 뜨는 키워드 N개 (기존 유지)
     │
     ├─→ 각 키워드로 ↓
     │
[공급사 축]    내 공급사(domeggookSellerId)들의 상품을
     │         getItemList?id=셀러&kw=키워드(or ca=카테고리)로 조회
     │         = "이 트렌드에 맞는, 내가 실제 거래하는 공급사의 상품"
     │
[전체시장 축]  기존 키워드 전체 도매 검색(공급사 무관, 신규 발굴용)
     │
     ▼
[통합 스코어러]  각 후보에 SEO 다차원 태그 + 공급사 프리미엄 가점
     ▼
[10개 엄선]    공급사 매칭 우선(내가 뗄 수 있음) + 트렌드 신규 발굴 섞어
     ▼
[디스코드 요약] + [앱 상세]
```

### 3-2. 공급사 프리미엄 (핵심 차별점)

같은 트렌드 키워드라도, **내 공급사가 그 상품을 이미 취급**하면 가점:
- ✅ 거래 중인 공급사 = 배송·정산·합배송 이미 세팅됨(마찰 0)
- ✅ 공급사 등급(sellerLv)·기존 마진(defaultMargin) 알고 있음
- ✅ 합배송 가능(bundleCapable) 공급사면 배송비 이점

→ 추천 상품에 **"내 공급사 [OO] 취급" 배지** = 운영자가 "지금 당장 뗄 수 있는 것"을 즉시 인지.

### 3-3. SEO 다차원 태깅 (운영자 언급 분류)

기존 `recoType`(황금🏆/니치💎/시즌🗓️) 인프라 확장 → 다중 태그:
| 태그 | 판정 기준(기존 신호 재활용) |
|---|---|
| 🏆 황금키워드 | 검색량 高 + 경쟁 低 (blueOceanScore 상위) |
| 💎 니치 | 검색량 中 + 경쟁 極低 + 진입장벽 低(entryBarrier) |
| 🌊 블루오션 | blueOceanScore ≥ 70 |
| 🔥 레드오션 주의 | 경쟁 高 + uniqueSellersInTop 多 |
| 🍯 꿀통상품 | 마진 우수(supplyPriceRange 대비 예상 판매가) |
| 📈 급상승 | 트렌드 상승률 상위 |
| 🏪 내 공급사 | domeggookSellerId 매칭됨 (공급사 프리미엄) |

### 3-4. 디스코드 = 모바일 요약, 앱 = 완결 (UX 핵심)

**디스코드**(모바일 3초 스캔 — 상품당 3줄):
```
🌷 꼬띠의 오늘 소싱 밭 (8/8)
오늘 10개 · 내 공급사 매칭 4

🏆🏪 차량용 방향제  블루오션 82
   🔍8,900 · 공급 3,200~5,800원 · [OO상사]
   💎 니치 · 🍯 마진우수

🔥 무선 가습기  레드오션 41
   경쟁 치열 — 차별화 필수

… (10개)
👉 앱에서 전체 확인·소싱 [바로가기]
```
- 상품명 + 핵심 배지 2~3개 + 숫자 1~2개 + 공급사명만. 정원 컨셉은 헤더 인사만(judgment surface는 명확하게, #318).
- 나머지(마진 계산·도매 매칭 목록·카테고리 정밀화 categoryMismatch·경쟁 상세·낙점 버튼)는 전부 앱.

**앱**(성장·소싱 화면 확장):
- 디스코드 10개가 그대로 앱 소싱 위젯에 연동(이미 SourcingRecommendWidget 존재).
- 각 상품 카드: 트렌드 지표 + 공급사 매칭 정보 + categoryMismatch 경고(트랙③) + 도매 매칭 + 낙점.
- 공급사 매칭 상품은 "이 공급사에서 바로 소싱" 딥링크.

## 4. 💡 확장 아이디어 — 품절 대체상품 연계

### 4-1. 품절 → 같은 공급사 대체 후보 (자동)
내 상품이 공급 단절(`source-gone.ts` 판정)되면:
- 그 상품의 공급사(domeggookSellerId)로 `getItemList?id=셀러&ca=같은카테고리` 조회
- = **같은 공급사·같은 카테고리의 살아있는 상품**(API가 품절 제외하므로 자동으로 판매중만) → 대체 후보
- 배송·정산 세팅이 이미 같은 공급사라 전환 마찰 최소
- 소싱 추천 파이프라인과 **동일 엔진 재사용**(전 상품 공통 #62)

### 4-2. "대체 소싱 카드" — 소싱 추천에 품절 대응 슬롯
데일리 10개 중 일부를 "내 품절 상품의 대체 후보"로 동적 할당:
- 품절 상품이 있으면 → 대체 후보를 우선 추천(급함)
- 없으면 → 신규 트렌드 발굴로 채움
- 운영자 관점: "당장 매출 구멍(품절) 메우기" > "신규 발굴" 우선순위 반영

### 4-3. 추가 제안 (Co-Founder 관점)
- **소싱 히스토리 학습**: 운영자가 낙점(interested/sourcing_started)한 상품의 카테고리·공급사·가격대를 학습 → 다음 추천 개인화("당신이 자주 뗀 [주방용품] 카테고리 신상").
- **경쟁 진입 타이밍**: 급상승 트렌드(📈)는 "지금 안 들어가면 레드오션 됨" 경고 → 선점 압박 UX.
- **합배송 번들 제안**: 같은 공급사에서 여러 상품 추천 시 "합배송 가능 — 배송비 절감" 묶음 제안(bundleCapable 활용).

## 5. 전 상품 공통 시스템 관점

단건 기능이 아니라 **소싱 파이프라인 구조 개편**:
```
                    ┌─ 트렌드 축(기존) ─┐
소싱 엔진 통합 ─────┼─ 공급사 축(신규) ─┼→ 통합 스코어(SEO 다차원+공급사 프리미엄)
                    └─ 전체시장 축 ─────┘         ↓
                                          10개 엄선 → 디스코드 요약 + 앱 상세
품절 판정(source-gone) ────────────────────→ 대체 후보(같은 공급사) ─→ 소싱 슬롯 재활용
낙점 히스토리 ──────────────────────────────→ 개인화 학습
```
- 공급사 축·품절 대체·개인화가 **하나의 소싱 엔진**을 공유(중복 구현 없음).
- 개입점: 소싱 위젯(앱)·디스코드(알림)·품절 대응 큐(operator action)에 자연스럽게 노출.
