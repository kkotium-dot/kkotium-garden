- Given 부속품밖에 없는 키워드, Then 배제하지 않고 경고와 함께 노출(정보 손실 방지 #327).

| 축 | 질문 | 기존 구현 | 예시 |
|---|---|---|---|
| priceOutlier (#326) | 가격이 묶음에서 이탈? | `wholesale-matcher.ts:218` | 캐리어 90원(리모컨 부속) |

## 3. 방안별 실현가능성 평가

### 방안 A — 도매처 카테고리 코드 활용 ★
**핵심 실측**:
- `getItemList ver4.1`은 **`ca`(카테고리) 파라미터를 입력으로 받는다**(웹 공식 레퍼런스 확인). 즉 카테고리로 검색을 좁힐 수 있다.
- 그러나 현행 `getItemList` **응답 item에는 카테고리 코드가 없다**(실측: item 필드 = `unitQty`·`price`·`title`뿐, `wholesale-matcher.ts:142-149`). 목록 응답만으로는 각 상품의 카테고리를 모른다.
- **상품상세 API(getItemView)**는 카테고리를 포함할 가능성이 높으나 실측 미확인 → **confidence: medium**.
- 이미 `dome-category-cache.ts`에 `DomeCategory`(카테고리 트리)·`CategoryMapping`(name_hash 학습 캐시)이 존재 → **인프라가 이미 있다**(COLLABORATION_PLAYBOOK #1 기존 활용).

| 하위안 | 방법 | 실현성 | 정확도 | 난이도 |
|---|---|---|---|---|
| A-1 목록 카테고리 분포 | 응답에 ca 없어 불가(현행) | ❌ | — | — |
| **A-2 `ca` 파라미터 역방향** | 키워드의 기대 카테고리를 알면 `ca`로 검색 범위 제한 | △ 기대 카테고리를 어떻게 아느냐가 순환문제 | 높음 | 중 |
| **A-3 상세 API 카테고리** | 상위 후보만 getItemView로 카테고리 확인 → 다수결에서 벗어난 것 경고 | ✅ 가능(medium) | 높음 | 중(호출 N배) |
| A-4 name_hash 캐시 재사용 | 기존 CategoryMapping으로 상품명→카테고리 추정 | ✅ 캐시 히트시 | 중 | 낮음 |

> A의 결론: **A-3(상세 카테고리 다수결) + A-4(캐시)** 조합이 현실적. 단 상세 API 호출 비용(상위 5~10건만 제한)과 getItemView 카테고리 필드 실측이 선결.

### 방안 B — 형태소·수식어 분석
- "귀청소기" = `[수식어 "귀"] + [키워드 "청소기"]`. 상품명이 `[한정어]+[키워드]` 패턴이고 한정어가 **신체부위·용도한정·대상한정어**면 다른 카테고리 의심.
- 규칙 기반(형태소 분석기 없이): 키워드 앞에 붙은 접두 토큰을 신체부위/동물/장소 사전과 대조.
- **신호어 사전 예시**(범용, 하드코딩 아님): 귀·코·발·두피·반려·강아지·고양이·어항·수족관·차량·자동차·하수구·변기…
- 장점: 도매 API 추가 호출 0(상품명만으로). 단점: 사전 커버리지 한계, "귀여운청소기" 같은 오탐 가능.

| 평가 | |
|---|---|
| 실현성 | ✅ 즉시(상품명 파싱만) |
| 정확도 | 중(사전 의존, 신조어 놓침) |
| 난이도 | 낮음(accessoryRisk와 동일 패턴) |

### 방안 C — 대표 상품 유사도
- 검색 결과 중 "가장 전형적 본품"(최다 등록·중앙가)을 기준으로 나머지의 상품명 토큰 겹침·가격대 비교.
- 문제: "청소기" 결과에서 귀청소기가 다수면 기준 자체가 오염됨. 기준 선정이 순환문제.
- priceOutlier와 상당 부분 중복(가격 이탈은 이미 잡음).

| 평가 | |
|---|---|
| 실현성 | △(기준 선정 취약) |
| 정확도 | 중~하 |
| 난이도 | 중 |

### 방안 D — 조합 (권장 골격)
- 기존 priceOutlier + accessoryRisk + **신규 categoryMismatch**.
- categoryMismatch = **B(수식어 사전, 저비용 1차) + A-3(상세 카테고리, 고정밀 2차 확인)** 계층.

## 4. ★ 권장안 — 리서치 근거 업그레이드 (2026-08-07, 외부 리서치 반영)

> 전체 리서치 원문: `docs/design/KOREAN_ECOMMERCE_CATEGORY_SIGNAL_RESEARCH_2026-08-07.md`. 이 섹션은 그 리서치의 결론을 이 설계에 통합한 것.

### 4-0. 리서치가 바꾼 것
운영자 지시로 "내 직관 사전이 아니라 업계 실무 기준"을 확인했다. 핵심 발견 2가지가 원래 권장안(B+A-3 하이브리드, 후순위+경고)을 **강화**했다:
1. **한국 소싱 툴(아이템스카우트·셀러픽·셀러라이프 등)은 이 문제를 전용 기능으로 안 푼다.** 아이템스카우트의 "대표 카테고리"는 표시 지표일 뿐 자동 필터가 아니고, 실무는 엑셀 수동 삭제로 우회한다. → **이 기능은 시장에 없는 차별화 포인트**이며, 참고할 "국내 툴의 검증된 알고리즘"이 없으므로 우리가 원리부터 설계해야 한다.
2. **네이버쇼핑 자체 분류(약 85%)·버즈니(3차 카테고리 90%대, 1차 카테고리 100%에 가까움)** 사례가 "대분류(1차) 판별은 규칙+계층 매핑만으로도 매우 신뢰할 만하다"를 뒷받침 → §7-A에서 확인한 **categoryCode 5단계 계층(대_중_소_세_세세)의 대분류(앞 2자리) 비교**가 정확도 높은 1차 신호로 검증됨.
3. **UX는 하드 배제가 아니라 신뢰도 등급(confidence tier) 기반 강등**이 업계 표준(아마존 browse node·검색 벤더 공통). 완전 배제는 오탐 시 진짜 본품을 잃는 비용이 커 이탈을 유발한다(Baymard 이탈률 통계로 뒷받침).

### 4-1. 판정 흐름 — 3단계 신뢰도 등급 (배제 아님 · #327 정신 강화)
```
1차 [수식어 사전 · 저비용, 상품명만]
    상품명이 [축A~F 블랙리스트 수식어] + [키워드] 패턴
    && 그 수식어가 키워드의 화이트리스트(정상 하위속성)에 없음
    → categoryMismatch: 'suspect' (사전만 매칭)

2차 [카테고리 대분류 대조 · 선택, getItemView 재사용]
    suspect 상위 N건만 categoryCode 앞 2자리(대분류) 확인
    → 키워드 결과의 최빈 대분류 접두와 다르면 → 'confirmed' (사전+대분류 모두 불일치)
    → 같으면 → 'cleared' (사전은 걸렸으나 실제 카테고리는 같음 — suspect 해제)

정렬  cleared/mismatch없음 우선 → suspect 후순위 → confirmed 최후순위(기본 접힘)
표시  suspect="다른 카테고리 의심" 배지, confirmed="다른 카테고리(예: 자동차용품) 확인됨" 배지
      confirmed도 삭제 안 함 — "숨긴 항목 N개 보기" 토글로 항상 복원 가능(#327 정보손실 금지)
```

**리서치 근거의 임계값 규칙** (한국 이커머스 소싱 리서치 §Recommendations):
- **강등→배제 승격 조건은 존재하지 않음** — 이 앱은 완전 자동 배제를 쓰지 않는다(운영자 원칙 #46·#307과도 정합: 자동 판단이 판매 기회를 임의로 차단하지 않음). confirmed도 "기본 접힘"까지만.
- **접힘→강등 완화 조건**: 특정 수식어의 오탐 신고(운영자가 "이거 아닌데" 피드백)가 누적되면 그 수식어를 화이트리스트로 이동.
- **1단계(사전)→2단계(대분류 대조) 착수 신호**: 사전만으로 안 잡히는 오염(수식어 없이 카테고리가 다른 케이스, 예: "청소솔"처럼 head noun 자체가 다른데 검색에 걸린 경우)이 유의미하게 관찰되면 2차 도입. 초기엔 1차만으로 시작 가능(API 호출 0).

### 4-2. 왜 이 조합인가 (리서치로 강화된 근거)
- **B(수식어 사전)를 1차**로: API 추가호출 0, 즉시 대다수 케이스 커버. accessoryRisk와 같은 사전 패턴이라 구현 일관성. **리서치가 확인**: SEO 업계도 "수식어→의도 클래스" 매핑이 표준 관행(how/what→정보성처럼), 같은 발상을 카테고리 전환에 적용.
- **대분류 대조를 2차·선택**으로: §7-A 실측(categoryCode 계층 구조)과 결합해, 전체 코드 일치가 아니라 **대분류 2자리만 비교**하는 관대한 기준 → 정상 세분류 차이를 오탐하지 않으면서도 버즈니 사례 수준(1차 분류 near-100%)의 신뢰도 기대 가능.
- **3단계 신뢰도 등급 UX**: 리서치가 확인한 "완전 배제는 이탈 유발" 원칙을 반영해, 기존 설계(2단계: suspect/confirmed)를 **cleared 단계를 추가한 3단계**로 세분화 — 사전이 걸어도 실제로 같은 카테고리면 정상 노출로 되돌리는 안전장치.

### 4-3. 핵심 원칙 준수
- **하드코딩 금지**: 특정 상품이 아니라 범용 사전(#55) — 아래 §4-4 6개 축.
- **키워드 자체가 한정어면 무시**: 소싱 키워드가 "귀청소기"면 "귀"를 한정어로 안 봄(accessoryRisk의 키워드-스킵과 동일 로직 :55).
- **완전 배제 금지**: confirmed도 삭제 아님, 토글로 항상 접근 가능(#327 강화).

| **E. 연령/사용자** | 출산/육아·시니어 전용 | 유아·아기·신생아·아동·어린이·시니어·노인·임산부 |
| **F. 소재/형태 축소어** | 완구/취미(모형) | 미니어처·모형·장난감·완구·피규어·인형용 |

**화이트리스트(정상 하위속성, 전환 아님 — 반드시 함께 관리)**: 무선·유선·스틱·핸디·진공·로봇·침구·차이슨 등 브랜드/방식/타입어. "미니"는 축 F와 겹치되 맥락 의존이라 head noun별 검토 필요(리서치 Caveats).

**경계 사례(하드코딩 금지 근거)**: "차량용 청소기"는 실제로 판매자 재량에 따라 `디지털/가전 > 청소기 > 핸디청소기`에도, `생활/건강 > 자동차용품`에도 등록됨(리서치 §Details 확인). → 이래서 **확정 배제가 아니라 확률적 신호(강등)**로 다뤄야 한다는 리서치 결론이 §4-1 3단계 등급 설계의 직접 근거.

### §7-A. getItemView 카테고리 실측 결과 (2026-08-07 Desktop)
**방법**: 실제 도매매 상품 2건을 앱 crawl API(`/api/crawl`, getItemView ver4.5)로 프로덕션 크롤링해 응답 필드 확인. 유효 상품번호는 도매매 메인에서 실제 추출(40159854·66003015).

**결과 — 카테고리 확실히 반환됨**:
| 상품 | categoryName | categoryCode |
|---|---|---|
| 여름 스포츠 얇은 양말 10개세트 | 스포츠양말 | `01_15_01_04_00` |
| 국산 후드형 쟈가드 햇빛가리개 | 사파리모자 | `01_09_08_00_00` |

**핵심 발견 3가지 (설계에 직접 반영)**:
1. **응답 구조 확정**: `domeggook.category.current.{name, code}`. 이미 `crawl/route.ts:76,100-101`에서 파싱 중(인프라 존재 확인). A-3는 새 API가 아니라 **기존 크롤 경로 재사용**으로 구현 가능 → 난이도 하향.
2. **★ categoryCode는 5단계 계층 구조** (`대_중_소_세_세세`, 예 `01_15_01_04_00`). 이건 설계를 강화한다 — "청소기" 정상 상품군과 "귀청소기"는 **대분류(앞 2자리 `01_XX`)부터 다를 가능성**이 높아, 전체 코드 일치가 아니라 **접두 N단계 일치**로 유연하게 판별 가능. 다수결(A-3)을 "가장 흔한 대분류 접두"로 잡으면 오염에 더 강함.
3. **A-3 판정 정밀화 제안**: suspect 후보의 categoryCode 접두(예 앞 2~3단계)가 그 키워드 결과의 **최빈 접두**와 다르면 confirmed. 완전 코드 일치보다 관대해 정상 변형(같은 카테고리 내 세분류 차이)을 오탐하지 않음.

**구현 영향**: §3 방안 A-3의 confidence가 medium → **high**. §6 write set의 "(선택) dome-category-cache.ts getItemView 헬퍼"는 이미 crawl 경로에 존재하므로 **신규 작성 최소**. 단 A-3 호출 상한(상위 N건)·rate 정책은 여전히 선결(2번째·3번째 체크박스).


## 8. 결론 요약
- SE05로 네이버 역조회 불가 → **도매처 자체 카테고리**가 유일 근거.
- **권장: B(수식어 사전 1차) + 대분류 대조(2차 선택) — 3단계 신뢰도 등급**(suspect/confirmed/cleared). 후순위+경고, 완전 배제 없음(§4-1).
- 구현은 기존 accessoryRisk 패턴 복제라 난이도 낮음. write set은 `wholesale-matcher.ts` 중심, 다른 레인 무간섭.
- **리서치로 확인**: 국내 소싱 툴(아이템스카우트 등)에 참조할 기존 기능이 없어 이건 시장 차별화 포인트다. 네이버쇼핑/버즈니 사례가 "대분류 판별은 규칙+계층 매핑으로 고신뢰"임을 뒷받침.
- **선결 3건 전부 해소**(§7): getItemView 카테고리 필드 CONFIRMED · 한정어 사전 6개 축 확정(§4-4) · 2차 호출 상한 5건. **구현 착수 가능.**
