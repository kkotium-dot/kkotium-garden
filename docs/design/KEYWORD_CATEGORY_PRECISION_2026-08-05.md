## 1. 문제 축 정리 — 이건 세 번째 축이다

기존 2축에 **카테고리 축**을 더한다. 셋은 서로 독립(하나로 다른 걸 못 잡음).

| 축 | 질문 | 기존 구현 | 예시 |
|---|---|---|---|
| priceOutlier (#326) | 가격이 묶음에서 이탈? | `wholesale-matcher.ts:218` | 캐리어 90원(리모컨 부속) |
| accessoryRisk (#327) | 본품이 아니라 부속품? | `detectAccessoryRisk()` :54 | 가습기→가습기청소솔 |
| **categoryMismatch (신규)** | **키워드와 다른 카테고리 상품?** | 없음 | 청소기→귀청소기(위생용품) |

> 왜 기존 축으로 안 잡히나: 귀청소기는 **가격 정상(priceOutlier X)** + **부속품 아님(본품이긴 함, accessoryRisk X)**. "청소기"라는 글자를 공유하는 **다른 카테고리의 본품**이라 제3축이 필요.

## 3. 방안별 실현가능성 평가

### 방안 A — 도매처 카테고리 코드 활용 ★
**핵심 실측**:
- `getItemList ver4.1`은 **`ca`(카테고리) 파라미터를 입력으로 받는다**(웹 공식 레퍼런스 확인). 즉 카테고리로 검색을 좁힐 수 있다.
- 그러나 현행 `getItemList` **응답 item에는 카테고리 코드가 없다**(실측: item 필드 = `unitQty`·`price`·`title`뿐, `wholesale-matcher.ts:142-149`). 목록 응답만으로는 각 상품의 카테고리를 모른다.
- **상품상세 API(getItemView)**는 카테고리를 포함할 가능성이 높으나 실측 미확인 → **confidence: medium**.
- 이미 `dome-category-cache.ts`에 `DomeCategory`(카테고리 트리)·`CategoryMapping`(name_hash 학습 캐시)이 존재 → **인프라가 이미 있다**(COLLABORATION_PLAYBOOK #1 기존 활용).

| 하위안 | 방법 | 실현성 | 정확도 | 난이도 |
|---|---|---|---|---|
| A-1 목록 카테고리 분포 | 응답에 ca 없어 불가(현행) | ❌ | — | — |
| **A-2 `ca` 파라미터 역방향** | 키워드의 기대 카테고리를 알면 `ca`로 검색 범위 제한 | △ 기대 카테고리를 어떻게 아느냐가 순환문제 | 높음 | 중 |
| **A-3 상세 API 카테고리** | 상위 후보만 getItemView로 카테고리 확인 → 다수결에서 벗어난 것 경고 | ✅ 가능(medium) | 높음 | 중(호출 N배) |
| A-4 name_hash 캐시 재사용 | 기존 CategoryMapping으로 상품명→카테고리 추정 | ✅ 캐시 히트시 | 중 | 낮음 |

> A의 결론: **A-3(상세 카테고리 다수결) + A-4(캐시)** 조합이 현실적. 단 상세 API 호출 비용(상위 5~10건만 제한)과 getItemView 카테고리 필드 실측이 선결.

### 방안 B — 형태소·수식어 분석
- "귀청소기" = `[수식어 "귀"] + [키워드 "청소기"]`. 상품명이 `[한정어]+[키워드]` 패턴이고 한정어가 **신체부위·용도한정·대상한정어**면 다른 카테고리 의심.
- 규칙 기반(형태소 분석기 없이): 키워드 앞에 붙은 접두 토큰을 신체부위/동물/장소 사전과 대조.
- **신호어 사전 예시**(범용, 하드코딩 아님): 귀·코·발·두피·반려·강아지·고양이·어항·수족관·차량·자동차·하수구·변기…
- 장점: 도매 API 추가 호출 0(상품명만으로). 단점: 사전 커버리지 한계, "귀여운청소기" 같은 오탐 가능.

| 평가 | |
|---|---|
| 실현성 | ✅ 즉시(상품명 파싱만) |
| 정확도 | 중(사전 의존, 신조어 놓침) |
| 난이도 | 낮음(accessoryRisk와 동일 패턴) |

### 방안 C — 대표 상품 유사도
- 검색 결과 중 "가장 전형적 본품"(최다 등록·중앙가)을 기준으로 나머지의 상품명 토큰 겹침·가격대 비교.
- 문제: "청소기" 결과에서 귀청소기가 다수면 기준 자체가 오염됨. 기준 선정이 순환문제.
- priceOutlier와 상당 부분 중복(가격 이탈은 이미 잡음).

| 평가 | |
|---|---|
| 실현성 | △(기준 선정 취약) |
| 정확도 | 중~하 |
| 난이도 | 중 |

### 방안 D — 조합 (권장 골격)
- 기존 priceOutlier + accessoryRisk + **신규 categoryMismatch**.
- categoryMismatch = **B(수식어 사전, 저비용 1차) + A-3(상세 카테고리, 고정밀 2차 확인)** 계층.

## 4. ★ 권장안 — B(1차 저비용) + A-3(2차 정밀) 하이브리드, 후순위+경고

### 판정 흐름 (배제 아님 · #327 정신)
```
1차 [수식어 사전 · 저비용]  상품명 = [한정어]+[키워드]?  → categoryMismatch: 'suspect'
2차 [상세 카테고리 · 선택]  suspect 상위 후보만 getItemView로 카테고리 확인
      → 다수 카테고리와 다르면 'confirmed', 같으면 'cleared'
정렬  본품(mismatch 없음) 우선 → suspect/confirmed 후순위
표시  suspect/confirmed에 "카테고리 확인 필요" 경고. 배제 안 함.
없으면 그거라도 노출(부속품밖에 없을 때처럼 정보 손실 방지)
```

### 왜 이 조합인가
- **B를 1차**로: API 추가호출 0, 즉시 대다수 케이스(귀·어항·하수구청소기) 커버. accessoryRisk와 같은 사전 패턴이라 구현 일관성.
- **A-3를 2차·선택**으로: B가 놓치거나 애매한 상위 후보만 상세 확인(호출 상한). 정밀도 보강.
- **후순위+경고**: 완전 배제하면 "키워드 자체가 귀청소기"인 정당 소싱을 죽인다(#327 규칙2와 동형). 운영자 최종 판단.

### 핵심 원칙 준수
- **하드코딩 금지**: 특정 상품이 아니라 "신체부위·동물·장소·기기대상" 한정어 **범용 사전**(#55).
- **키워드 자체가 한정어면 무시**: 소싱 키워드가 "귀청소기"면 "귀"를 한정어로 안 봄(accessoryRisk의 키워드-스킵과 동일 로직 :55).

### §7-A. getItemView 카테고리 실측 결과 (2026-08-07 Desktop)
**방법**: 실제 도매매 상품 2건을 앱 crawl API(`/api/crawl`, getItemView ver4.5)로 프로덕션 크롤링해 응답 필드 확인. 유효 상품번호는 도매매 메인에서 실제 추출(40159854·66003015).

**결과 — 카테고리 확실히 반환됨**:
| 상품 | categoryName | categoryCode |
|---|---|---|
| 여름 스포츠 얇은 양말 10개세트 | 스포츠양말 | `01_15_01_04_00` |
| 국산 후드형 쟈가드 햇빛가리개 | 사파리모자 | `01_09_08_00_00` |

**핵심 발견 3가지 (설계에 직접 반영)**:
1. **응답 구조 확정**: `domeggook.category.current.{name, code}`. 이미 `crawl/route.ts:76,100-101`에서 파싱 중(인프라 존재 확인). A-3는 새 API가 아니라 **기존 크롤 경로 재사용**으로 구현 가능 → 난이도 하향.
2. **★ categoryCode는 5단계 계층 구조** (`대_중_소_세_세세`, 예 `01_15_01_04_00`). 이건 설계를 강화한다 — "청소기" 정상 상품군과 "귀청소기"는 **대분류(앞 2자리 `01_XX`)부터 다를 가능성**이 높아, 전체 코드 일치가 아니라 **접두 N단계 일치**로 유연하게 판별 가능. 다수결(A-3)을 "가장 흔한 대분류 접두"로 잡으면 오염에 더 강함.
3. **A-3 판정 정밀화 제안**: suspect 후보의 categoryCode 접두(예 앞 2~3단계)가 그 키워드 결과의 **최빈 접두**와 다르면 confirmed. 완전 코드 일치보다 관대해 정상 변형(같은 카테고리 내 세분류 차이)을 오탐하지 않음.

**구현 영향**: §3 방안 A-3의 confidence가 medium → **high**. §6 write set의 "(선택) dome-category-cache.ts getItemView 헬퍼"는 이미 crawl 경로에 존재하므로 **신규 작성 최소**. 단 A-3 호출 상한(상위 N건)·rate 정책은 여전히 선결(2번째·3번째 체크박스).


## 8. 결론 요약
- SE05로 네이버 역조회 불가 → **도매처 자체 카테고리**가 유일 근거.
- **권장: 방안 D = B(수식어 사전 1차) + A-3(상세 카테고리 2차 선택)**. 후순위+경고, 배제 아님.

- A-3의 getItemView 카테고리 필드 = **CONFIRMED**(2026-08-07 Desktop 실측, §7-A). categoryCode 5단계 계층 구조 발견으로 접두 N단계 판별 가능 → A-3 confidence high. 남은 선결 = 한정어 사전 승인·A-3 호출 상한 정책.
