## 3대 기둥 (모든 작업의 헌법)

### 기둥 1 — 출처로 교차검증 (환각 제거)
**어떤 판단도 추측/보고/문서를 그대로 믿지 않고, 1차 출처로 실측한다.**
- 코드 판단 → git·실제 소스 파일. 상태 판단 → 프로덕션 API·DB. 시장/SEO 판단 → 웹 출처(날짜 확인).
- 인계/보고는 "검증 대상"이지 "사실"이 아니다. Code가 "완료"라 해도 Desktop이 실측으로 재확인.
- **핵심 구분**: 구조 검증 ≠ 내용 검증.
  - 예(2026-08-27): naver_categories FK 무결성 0 orphan(구조 OK)인데, 연결된 값이 아이스트레이→홍합·디퓨저→교자상(내용 오류). "FK 연결됨 ≠ 올바른 카테고리".
  - **하이브리드 관문(2026-09-01, 위 사고의 재발방지)**: 내용 검증을 사람 기억에만 의존하지 않는다.
    **A=사람관문**(운영자 GO 없이 `--apply` 금지, 작업원칙 #41) + **B=기계관문**(tsx 정합성 테스트가 값을 assert,
    `npm run test:category-integrity` — `scripts/verify-category-integrity.ts`). A만으로는 "이번엔 맞겠지"라는
    확인 피로가 재발을 부르고, B만으로는 애매한 케이스의 최종 판단(운영자 GO)이 빠진다. 둘 다 있어야 완료
    (`docs/playbook/COMPLETION_GATE.md` 카테고리 작업 특칙).
- 내가 틀릴 수도 있다: 내 검증 쿼리가 틀린 컬럼을 봐서 오탐 낸 적 있음(같은 날 category_code vs id). 실측도 재검증한다.
- 없는 걸 지어내지 않는 것도 정확도다: 마스터에 없는 상품은 빈손+정직표시가 정답(무드등). 억지 매칭이 오류.

### 기둥 2 — 단건 수습 금지 (근본·시스템 승격)
**증상 하나를 고치지 말고, 뿌리를 찾아 시스템 레벨로 승격한다.**
- 오류 발견 시 "이 상품만"이 아니라 "이 로직을 쓰는 모든 경로"를 점검(#62).
- 반복 위험이 있으면 원칙/개입점으로 박제:
  - 예: 캐시 포이즌(수동 DELETE) → logic_version 자동무효화 + 원칙 #351.
  - 예: 워크트리 방치 → 원칙 #347 + COMPLETION_GATE C6.
- "같은 뿌리"는 한 작업으로 병합: z-score 편중 + 소싱 카테고리 오라벨 = 둘 다 렌즈 d1 오용 → 병합 수정.
- 하나의 발견이 여러 문제의 뿌리일 수 있다: naver_categories 0행 = 미발행 category_id 공백 + 발행넛지 막힘 + UCE DB 부채의 공통 뿌리.

### 기둥 3 — 전 상품 공통 시스템 (범용·개입점 내재화)
**특정 상품이 아니라 "어떤 상품이 올라와도" 작동하는 엔진으로 설계한다.**
- 상품별 하드코딩 금지. 상품데이터 → 구조 자동생성(UCE 매처·AEO 프롬프트·발행넛지).
- 검증은 카탈로그 밖 임의 상품으로: 12개가 아니라 "무드등·스텐빨대·수세미" 등 임의 20종으로 정확도 실측.
- 개입점을 자연스럽게 녹인다: 실패/모호 상품은 "확인 필요" 큐로 surface(강제 순서 아님, #56).
- 완료조건 = 존재가 아니라 정확도: "suggestions 비어있지 않음"이 아니라 "맞는 카테고리인가".
- **테스트 green ≠ 전수 안전(#352)**: 테스트/정합성검사가 통과해도 그건 "그 케이스만" 안전한 것. 비가역 쓰기(DB backfill·일괄 UPDATE)는 반드시 (1)카탈로그 밖 임의 20종+ 전수 dryRun 오분류0 + (2)실 카탈로그 전수 dryRun 개악0 + (3)회귀테스트 고정 후에만 --apply. dryRun 없는 비가역 쓰기 금지.
- **개악 > 미개선**: 원래 맞던 값을 틀리게 바꾸는 건 빈손 유지보다 나쁘다. 확신 없으면 NULL(정직)이 개악보다 낫다.

## 착수·검증·완료 체크 (3기둥의 실행형)

**착수 전**: DOMAIN_FACTS·CLAUDE·TRACKER·PRINCIPLES 읽음? write set 충돌 없나(병렬 안전)? 운영자 GO 필요한가?
**검증 시**: 실측했나(문서/보고 아님)? 구조뿐 아니라 내용도? 카탈로그 밖 임의 표본으로? 회귀 0?
**완료 시**: COMPLETION_GATE C1~C6(해시·병합·연결·데이터·실행·워크트리위생). 프로덕션 실효까지? 브라우저 실측?

## 학습 축적 규약 (이 문서의 목적 = 계속 자라게)

매 세션의 핵심 통찰은 아래 규칙으로 축적한다:
1. **재사용 방법론** → 이 문서(CORE_WORKING_PRINCIPLES) 또는 docs/playbook/*.
2. **번호형 세부 원칙** → PRINCIPLES_LEARNED.md(#다음번호). 근거(날짜·사건) 명시.
3. **반복 실패 패턴** → REPEATED_FAILURE_PATTERNS.md.
4. **진단 절차** → docs/playbook/*_DIAGNOSIS.md (예: AI_DEPENDENCY_DIAGNOSIS).
5. 세션 종료 시 #319대로 문서 3종(CURRENT·TRACKER·PRINCIPLES) 갱신 = 완료조건.

> 원칙: 통찰은 "말"이 아니라 "커밋된 문서"로 남을 때만 학습이다. 다음 세션이 이 문서를 읽고 같은 실수를 안 하면 성공.
