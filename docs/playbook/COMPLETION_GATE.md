## 왜 이 문서가 필요한가

2026-08-19 ~ 08-20 이틀 사이에 **같은 유형의 실패가 5회** 발생했다.
전부 "작업은 실제로 했는데, 사용 지점에 반영되지 않은" 경우다.
tsc는 통과했고, 코드도 옳았고, 보고도 "완료"였다. 그런데 아무 효과가 없었다.

이건 개인의 부주의가 아니라 **완료 판정 기준의 부재**다. 그래서 규칙으로 막는다.

## 규칙 — 완료 판정 5게이트

어떤 작업이든 "완료"라고 말하기 전에 아래를 **명령 실행 결과로** 증명한다.
해당 없는 항목은 "해당 없음"이라고 명시한다. 침묵은 미통과로 간주한다.

### G1. 커밋 게이트 — 도장이 찍혔는가
```bash
git status --porcelain        # 결과가 비어 있어야 함
git log -1 --format='%h %s'   # 해시를 보고에 포함
```
- ✅ 통과 조건: 변경분이 커밋되고 **해시를 보고에 명시**
- ❌ **해시 없는 완료 보고는 완료로 인정하지 않는다**

### G2. 병합 게이트 — main에 들어갔는가
```bash
git merge-base --is-ancestor <hash> origin/main && echo MERGED || echo NOT-IN-MAIN
```
- ✅ 통과 조건: `MERGED`
- ⚠️ 브랜치 커밋은 "작업 보존"이지 "반영"이 아니다. 배포되는 것은 main뿐이다

### G3. 연결 게이트 — 실제로 호출되는가
```bash
grep -rn "<새 함수/모듈명>" src/ --include=*.ts --include=*.tsx | grep -v "<정의 파일>"
```
- ✅ 통과 조건: 호출부가 **1건 이상**, 그 위치를 보고에 명시
- ❌ 파일 생성 + tsc 통과는 완료가 아니다. **호출부 없는 모듈은 죽은 코드다**
- 참고: 작업원칙 #292(죽은 코드는 결함의 냉동고다)의 사전 차단판

### G4. 데이터 게이트 — 입력이 존재하는가
```sql
-- 새 로직이 읽는 컬럼/테이블의 실제 채움률을 센다
SELECT count(*) AS 전체, count(<대상컬럼>) AS 값있음 FROM <테이블>;
```
- ✅ 통과 조건: 로직이 의존하는 데이터가 실제로 존재
- ❌ 전 건이 기본값/NULL로 떨어지면 그 로직은 **작동하지 않는 것**이다
- 예: `dropship-fitness`가 D1을 읽는데 D1이 전부 NULL → 감점 로직 무효

### G5. 실행 게이트 — 결과가 기대와 같은가
```bash
# 실제로 돌리고, 출력값을 보고에 그대로 붙인다
npx tsx scripts/<verify-script>.ts
```
- ✅ 통과 조건: 실행 출력값을 보고에 **원문 그대로** 포함
- ❌ "잘 될 것으로 보입니다" 금지. 실행 못 했으면 **"실행 못 했다"고 명시**
- ✅ 환경 한계로 실행 불가 시: 검증 스크립트를 만들어 실행 가능한 레인에 인계

### 문서 작업 특칙 (F5 재발 방지)
설계안·리서치·인계 문서를 **작성만 하고 커밋하지 않으면 다른 레인에서 보이지 않는다.**
- 문서를 근거로 인계할 때는 **커밋·push 후 해시와 함께** 전달한다
- 인계받은 쪽은 문서가 없으면 **요약만 보고 착수하지 말고 부재를 먼저 보고**한다
  (2026-08-20 Code의 대응이 이 원칙의 모범 사례)

## 검증 우선순위 — 어디부터 의심하는가

문제가 생겼을 때 이 순서로 확인한다. 위쪽일수록 흔하고 확인이 싸다.

```
1. main에 있나?        git merge-base --is-ancestor
2. 커밋됐나?           git status --porcelain
3. 호출되나?           grep 호출부
4. 데이터가 있나?      SELECT count(*)
5. 배포됐나?           프로덕션 SHA 대조
6. 그 다음에 코드 로직을 의심한다
```

**1~5를 건너뛰고 6부터 파면 시간을 잃는다.**
2026-08-12~19 소싱 알림 8일 미스터리가 그 사례다 — 코드는 처음부터 옳았고,
문제는 관측 수단 부재와 확인 타이밍이었다.
