# AI 의존 기능 진단 플레이북 — "기능이 조용히 침묵할 때"

> **작성일** 2026-08-27 | **레인** Code | **성격** 재사용 진단 절차(원칙 해설 아님)
> **관련 원칙** #348 · #349 · #350 (해설은 `docs/plan/PRINCIPLES_LEARNED.md`)
>
> 이 문서는 **"AI 호출 기능이 기대와 다른 결과(빈 값·폴백·저품질)를 낼 때 무엇을
> 이 순서로 확인할 것인가"**만 담는다. UCE(Universal Category Engine) 세션에서
> `category/suggest`의 `usedAI:false`를 파싱 버그로 의심했다가, 실제로는
> Groq가 `llama-3.3-70b-versatile`을 카탈로그에서 완전히 제거해 앱 전역 Groq
> 호출이 전부 404였던 사례(2026-08-27)에서 이 절차를 정리했다.

---

## 진단 순서 (반드시 이 순서로 — 역순으로 하면 시간 낭비)

```
① 기능 침묵/저품질 관측
       ↓
② 표면 신호를 실패로 단정하지 않는다 — 코드 반환조건부터 읽는다 (#350)
       ↓
③ 그래도 원인 불명이면 외부 의존성(모델/API) 생존을 확인한다 (#348)
       ↓
④ 확신이 안 서면 런타임 로그를 실측한다 (배포된 코드가 맞는지도 함께 확인)
       ↓
⑤ 근본수정
       ↓
⑥ 결정론적 폴백을 1순위로 재배선해 재발 시 침묵하지 않게 한다 (#349)
```

---

## ① 관측: 무엇이 이상한가

- AI 응답이 빈 값/기본값/폴백으로만 나온다
- `usedAI:false`, `source:fallback`, 에러율 급증 같은 메타 필드가 평소와 다르다
- 품질이 갑자기 나빠졌다(예: 이상하게 짧은 응답, 다른 언어 섞임)

이 시점에서 "AI가 고장났다"고 단정하지 말 것 — ②로 간다.

---

## ② 표면 신호 실패단정 금지 (#350)

- [ ] 그 값을 **어떤 코드가 왜 반환했는지** 먼저 읽는다 (`grep`으로 반환 지점 특정)
- [ ] early return·가드 조건이 있다면, **이 입력값에서는 원래 그게 정상 동작인지** 확인
- [ ] 같은 엔드포인트를 **다른 입력으로 재현** — "이 조건에서만 폴백"인지 "항상 폴백"인지 구분
- [ ] 항상 폴백/항상 실패라면 ③으로 진행

```bash
# 예: source 필드를 세팅하는 모든 지점을 한 번에 확인
grep -n "source = \|source:" src/app/api/<route>/route.ts
```

## ③ 외부 의존성(모델/API) 생존 확인 — 최우선 의심 대상 (#348)

**왜 최우선인가**: 확인 비용이 API 호출 1번으로 가장 싸고, 문제가 있을 경우
영향 범위가 그 모델/API를 쓰는 **모든 기능**이라 가장 크다.

- [ ] 모델명이 코드에 하드코딩돼 있는지, 아니면 단일 상수로 격리돼 있는지 확인
      (여러 곳에 흩어져 있으면 전체 grep으로 모으기)
- [ ] provider의 현재 카탈로그를 직접 조회한다:
```bash
# Groq 예시 — 다른 provider는 해당 SDK/REST의 모델 목록 엔드포인트 사용
curl -s https://api.groq.com/openai/v1/models -H "Authorization: Bearer $GROQ_API_KEY" \
  | node -e "let d='';process.stdin.on('data',c=>d+=c);process.stdin.on('end',()=>{const j=JSON.parse(d);console.log(j.data.map(m=>m.id).join('\n'))})"
```
- [ ] 코드가 쓰는 모델명이 이 목록에 **정확히** 있는지 대조 (오타·구버전명 주의)
- [ ] 없다면: 대체 모델을 찾아 **실제 프롬프트로 라이브 테스트**한 뒤 교체
      (형식·언어 품질을 직접 확인 — 특히 최근 모델은 reasoning 모델일 수 있어
      `reasoning_effort`/`max_tokens` 조정이 별도로 필요할 수 있다, 2026-08-27 사례)

## ④ 런타임 로그 실측 — "고쳤다"고 믿기 전에

- [ ] `vercel logs <domain> --since <기간>` (또는 해당 플랫폼의 실 로그)으로
      **에러 메시지 원문**을 확인한다 — 추측한 원인과 실제 에러 문구가 다를 수 있다
- [ ] 로그의 에러 문구를 **현재 소스 코드의 문구와 대조**한다 — 로그가 옛 문구를
      그대로 뱉고 있다면, 애초에 배포가 반영 안 됐을 가능성을 먼저 배제한다
      (`git log -1 --format=%H` vs 배포 메타의 `githubCommitSha` 직접 대조 —
      `vercel ls --json` 응답이 클 경우 파이프 버퍼에 잘려 오탐할 수 있으니
      직접 `curl`/`node`로 파싱해 재확인)

## ⑤ 근본수정

- [ ] 모델명이 여러 곳에 하드코딩돼 있었다면 이번 기회에 **단일 상수로 격리**
- [ ] 수정 후 **실제 프롬프트로 라이브 재현 테스트** (성공 케이스 + 실패해야 하는
      케이스 둘 다 — 예: 확신 없는 입력에 정직하게 빈 배열을 반환하는지)

## ⑥ 결정론적 폴백 재배선 (#349) — 재발해도 침묵하지 않게

- [ ] 이 기능이 **유한한 정답 집합**(마스터 데이터)에 기반한 분류/매칭이라면,
      결정론적 매칭을 1순위로 두고 AI는 그게 실패했을 때만 보조로 부르도록
      재설계한다 — 외부 AI가 다시 조용히 죽어도 핵심 기능은 살아있다
- [ ] 안 된다면 최소한 **모델 생존을 주기적으로 확인하는 자동 점검**(예: 월간
      크론의 헬스체크 항목)을 추가해, 다음 폐기가 침묵이 아니라 알림으로
      드러나게 한다
