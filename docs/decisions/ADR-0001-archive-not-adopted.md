# ADR-0001: 보관함(ARCHIVE) 도입 보류 — 삭제 안전 판정으로 대체

> 상태: 승인 (2026-07-24)
> 결정자: 운영자 위임 → Desktop 권장안 확정

## 맥락

Cowork 초기 생애주기 설계에 `ARCHIVED` 상태와 `ARCHIVE`/`RESTORE` 액션이 포함됐으나, 실제 앱에는 미구현 개념이었다. 도입 여부를 결정해야 한다.

충돌하는 힘들:
- **찬성**: 삭제는 비가역이다. "지금은 안 팔지만 나중에 쓸지도"라는 상품을 목록에서 치우는 수단이 필요할 수 있다.
- **반대 1**: 이미 `disposition.ts`가 **자산 유무로 삭제 안전성을 판정**한다. 판매이력이 있으면 `RESOURCE`(대체소싱·삭제금지), 없으면 `DELETE_SAFE`(정리 안전). 즉 **"함부로 지워지는" 위험은 이미 막혀 있다.**
- **반대 2**: 상태를 하나 추가하면 **7개 화면 전부**에 배지·필터·액션 분기가 늘어난다. 지금 프로젝트의 최대 문제는 화면 간 판정 불일치이며, 상태를 늘리면 그 표면적이 커진다(#295 위반 위험 증가).
- **반대 3**: 1인 운영에서 "보관함"은 **두 번째 정원 창고**가 되기 쉽다. 정원 창고 자체가 이미 "발행 전 보관" 역할을 한다.
- **반대 4**: DB 필드 신설 + 마이그레이션이 필요하다.

## 결정

**우리는 보관함(ARCHIVE/RESTORE)을 도입하지 않는다.** 대신 기존 처분 판정을 신뢰한다.

- 미발행 상품 → 정원 창고가 보관 역할을 한다(별도 보관함 불필요).
- 발행 상품 중 안 파는 것 → `SUSPEND`(판매중지)로 스토어 노출만 끄고 앱에는 남긴다.
- 공급 끊긴 것 → `RESOURCE`(자산 있음·대체소싱) 또는 `DELETE_SAFE`(자산 없음·정리 안전).

**재검토 조건**: 운영 중 "지우기도 애매하고 판매중지도 아닌" 상품이 **10건 이상** 쌓이면 이 결정을 다시 연다.

## 결과

- **긍정**: 상태 7종 유지 → 화면 간 불일치 표면적이 늘지 않는다. DB 마이그레이션 0. 기존 자산보호 로직을 그대로 활용(PLAYBOOK #1 정합).
- **부정**: "임시로 치워두기"라는 중간 선택지가 없다. 판매중지 또는 삭제 둘 중 하나를 선택해야 한다.
- **중립**: `LIFECYCLE_BRIDGE_V2` §10의 미확정 항목 1건이 닫힌다. Cowork v1 설계의 `ARCHIVED`·`RESTORE`·T-06·T-07·T-10은 폐기 확정.
