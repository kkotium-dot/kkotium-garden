# ADR-0003: 검수 게이트 구현 4대 결정

> 상태: 승인 (2026-07-29)
> 결정자: 운영자 위임 → Desktop 권장안 확정
> 관련: `docs/design/PUBLISH_REVIEW_GATE_2026-07-23.md` · 원칙 #311 · #307

## 맥락

최초 발행 4경로(P0~P3) 어디에도 검수 게이트가 없다. 구현 착수 전 Code가 코드 실측으로 4개 미확정 사항을 보고했다. 특히 **파일명 충돌**은 그대로 두면 기존 로직이 사라지는 사고로 이어진다.

**실측 확인** (Desktop 2026-07-29):
- `src/lib/products/publish-gate.ts` **실재** (3,681 bytes, 07-22 생성)
- `checkPublishGate` = 공급처단절/공급사품절 판정 (`SOURCE_GONE` | `SUPPLIER_OUT_OF_STOCK`)
- 사용처 2곳: `products/page.tsx:1247` · `products/page.tsx:2056`

## 결정

### 결정 1 — 파일명 분리. 신규는 `publish-review-gate.ts`

**우리는 기존 `publish-gate.ts`를 그대로 두고, 신규 게이트를 `src/lib/products/publish-review-gate.ts`로 만든다.**

근거: 두 게이트는 **서로 다른 질문**에 답한다.
| 파일 | 질문 | 판정 |
|---|---|---|
| `publish-gate.ts` (기존) | **팔 수 있는 물건인가?** | 공급처 단절·공급사 품절 |
| `publish-review-gate.ts` (신규) | **팔아도 되는 상태인가?** | 검수 승인·준비도·이미지 경고 |

이름이 비슷하다는 이유로 합치면 판정 축 2개가 뒤섞인다(#300 상태축↔권고축 분리의 연장). 파일을 나누는 편이 나중에 읽을 때도 명확하다.

### 결정 2 — 두 게이트는 AND 결합. 단 **차단 사유는 분리 표시**

**우리는 발행 허용 조건을 `공급 가능 AND 검수 승인`으로 한다.**

근거: 공급이 끊긴 상품을 검수 통과했다고 발행하면 **품절 상품을 스토어에 올리는 것**이다. 반대로 공급이 멀쩡해도 검수 안 했으면 #307 위반. 둘 다 필요조건이다.

**단, 셀러에게 보여줄 때는 사유를 구분한다**(3초룰):
- 공급 문제 → "공급처가 끊겼어요 — 대체 소싱이 필요해요"
- 검수 문제 → "검수 대기 — 씨앗심기에서 확인하세요"

두 개를 "발행 불가"로 뭉뚱그리면 셀러가 **무엇을 해야 할지 모른다.** 진단은 각각, 처방도 각각.

### 결정 3 — P1 게이트는 **이미지 업로드 전(392줄 앞)**

**우리는 `register/route.ts`의 게이트를 이미지 업로드 이전 지점에 둔다.**

근거 3가지:
1. **네이버 대역폭·시간 낭비 방지** — 어차피 막힐 상품의 이미지를 올릴 이유가 없다.
2. **네이버 측 쓰레기 데이터 방지** — 업로드된 이미지가 상품 없이 남는다.
3. **실패 속도** — 셀러가 결과를 더 빨리 본다.

단, `dryRun`(218줄) 분기는 **게이트를 적용하되 차단하지 않고 사유만 반환**한다. 미리보기는 "지금 발행하면 왜 막히는지"를 보여주는 용도이므로, 여기서 막으면 진단 기능이 죽는다.

### 결정 4 — REVIEW_STALE은 **필드 화이트리스트** 기준

**우리는 `updatedAt` 전체가 아니라, 검수 대상 필드가 바뀐 경우에만 승인을 만료시킨다.**

화이트리스트(검수에서 실제로 보는 것):
- 상품명 · 카테고리 · 대표이미지 · 상세이미지 · 판매가 · 옵션

제외(검수와 무관):
- 재고 스냅샷 · 좀비 점수 · 마진 재계산 · 동기화 타임스탬프 · 조회수

근거: `updatedAt` 전체를 기준으로 하면 **재고 폴러가 하루 몇 번 돌 때마다 검수 승인이 풀린다.** 그러면 셀러는 발행할 때마다 재검수를 강요당하고, 결국 게이트를 꺼버리게 된다. **지킬 수 있는 규칙이라야 지켜진다.**

## 결과

- **긍정**: 기존 로직 무손실. 판정 축 2개가 분리 유지(#300). 불필요한 네이버 업로드 제거. 검수 승인이 실용적으로 유지됨.
- **부정**: 파일이 하나 늘어 "어느 게이트인지" 헷갈릴 여지 → 각 파일 상단에 한 줄 주석으로 역할 명시 필수.
- **중립**: 화이트리스트는 필드가 추가될 때 갱신이 필요하다. `publish-review-gate.ts` 안에 상수로 두고 주석으로 근거를 남긴다.

## 구현 시 필수 검증

1. **우회 경로 0건**(#311) — P0·P1·P2·P3 전부 `assertPublishable` 호출 확인
2. 기존 `checkPublishGate` 사용처 2곳(`page.tsx:1247`·`2056`) **동작 불변** 확인
3. `npx tsc --noEmit` 0 에러 + 기존 테스트 전량 통과
4. **네이버 실제 발행 금지** — 게이트 로직만 구현, 실발행 테스트는 운영자 GO 후(#46)
5. 배포 후 Desktop 프로덕션 실측 — 검수 안 한 상품이 발행 경로에서 실제로 막히는지
