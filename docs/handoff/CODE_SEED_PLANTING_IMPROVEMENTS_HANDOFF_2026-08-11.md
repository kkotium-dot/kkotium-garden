## #1. 원산지 정보 미연동 (최우선, 명확한 버그, 즉시 수정 가능)

### 근본 원인 확정 (Desktop 실측)
`Product` 스키마에 `naver_origin`(원산지 텍스트)·`originCode`(원산지 코드) 필드가 **이미 존재**하는데, `src/app/api/products/import/route.ts`가 이 둘을 **전혀 채우지 않는다.**

### 재사용 가능한 검증된 매핑 로직 (같은 프로젝트에 이미 있음)
`src/app/api/products/[id]/naver-detail/route.ts` 97-112행에 정확한 추출 경로가 이미 구현돼 있다:
```typescript
const originAreaInfo = (detailAttribute.originAreaInfo ?? {}) as Record<string, any>;
// ...
originAreaCode: originAreaInfo.originAreaCode ?? null,
importer: originAreaInfo.importer ?? null,
```
`op.detailAttribute.originAreaInfo.originAreaCode`가 정확한 경로. import route에 같은 추출 함수를 추가하고 `naver_origin`/`originCode` 필드에 매핑.

### 주의사항
- 네이버 `originAreaCode`(예: "0200037" 같은 코드)와 앱의 `originCode`가 **같은 코드 체계인지 먼저 확인** — 이전 세션 메모리에 "명화 원산지는 originCode '00'이 맞고 0200037로 바꾸면 안 됨"(#기존 원칙)이라는 사례가 있었다. **코드 체계가 다르면 오매핑 위험**이 있으니, 네이버 원산지 코드 체계와 앱 `Origin` 모델(`originCode`/`originName`, 385-386행)의 코드 체계를 먼저 비교해서 맞는지 확인 후 매핑할 것. 다르면 코드 변환 테이블이 필요할 수 있음 — 함부로 그대로 저장하지 말 것.
- `naver_origin`은 텍스트 필드로 보이니 `originAreaInfo`에서 사람이 읽을 수 있는 원산지명이 있다면 그쪽으로, `originCode`는 앱 내부 코드 체계에 맞게 변환 후 저장(맞는 코드가 없으면 비워두고 다음 라운드로 — #325 정직한 미달성).

### write set
`src/app/api/products/import/route.ts` (핵심) — 다른 파일 불필요.

## #2. "수정한 필드만 네이버에 부분 재연동" (신규 기능, 큰 스코프 — 설계 먼저)

### 현황 확정 (Desktop 실측)
현재 `naver-push/route.ts`는 **가격·재고 단일 필드만** 업데이트 가능(`field: 'price'|'stock'`). 상품명·설명·이미지·원산지·태그 등 **전체 상품 정보를 "바뀐 것만" 골라 네이버에 PUT하는 기능은 아직 없다.**

### 운영자 요청 정확히 재기술
"네이버에서 가져온 상품을 씨앗심기에서 수정 → 저장 시 **수정한 필드만** 네이버에 반영되고, 안 건드린 필드는 기존 네이버 값 그대로 유지"

### 설계 방향 (Code가 세부 설계 후 결과문서에 기록 — 이번 인계는 방향 제시까지)
1. **변경 감지**: 씨앗심기 폼이 열릴 때의 초기값(import/hydrate 시점 스냅샷)과 저장 시점 값을 비교해 "실제로 바뀐 필드"만 골라낸다. React 폼 상태에서 `dirty fields`를 추적하는 게 일반적 — 이미 폼에 초기값 로딩 로직이 있으니(hydrate), 그 초기 스냅샷을 저장해뒀다가 제출 시 diff.
2. **네이버 상품수정 API**: `PUT /v2/products/origin-products/{originProductNo}`가 전체 필드를 요구하는지, 부분 필드만 보내도 되는지(PATCH 시맨틱 지원 여부) 네이버 공식 문서로 먼저 확인 필요. **대부분의 네이버 API는 전체 객체를 요구하는 경우가 많다** — 그렇다면 "현재 네이버 값을 먼저 GET → 우리가 바꾼 필드만 덮어쓰기 → 전체를 PUT" 방식이 안전(부분 필드만 보내면 나머지가 null로 덮어써질 위험).
3. **안전장치**: 이 기능은 실제 네이버 상품 정보를 변경하는 **비가역 쓰기**다. 반드시 미리보기(어떤 필드가 바뀌는지 확인 화면) → 운영자 명시 확인(confirm) → 실행 순서를 지킬 것(#46 원칙, 기존 `naver-push`의 dryRun 패턴 참고).
4. **UI**: 씨앗심기 저장 버튼 근처에 "네이버에도 반영" 같은 명시적 액션으로 분리(자동 저장과 네이버 반영은 별개 동작이어야 함 — 로컬 저장은 즉시, 네이버 반영은 명시적 트리거).

### 이번 라운드 범위 제안
전체를 한 번에 다 하지 말고, **1단계: 설계 문서 작성 + 네이버 API가 부분/전체 어느 쪽인지 문서 조사**까지만 먼저 하고 Desktop에 인계 — 실제 구현(비가역 쓰기 포함)은 설계 승인 후 별도 라운드로.

### write set (설계 단계)
새 설계 문서만: `docs/design/NAVER_PARTIAL_SYNC_2026-08-11.md`. 코드 변경 없음.

## #3. 우측 패널(마진 계산기) 자동 계산 → 좌측 반영 여부 확인

### 요청
"오른쪽의 마진 및 꿀통 지수 AI 기능들이 입력했을 경우 왼쪽의 상품 폼에 적용되고 자동으로 계산되는 기능이 제대로 작동하는지" 확인.

### Desktop이 브라우저로 확인한 것 (참고)
우측 패널에 실전 마진 계산기(공급가·판매가 입력 → 순마진율·경쟁 채널별 마진 비교 4종 카드)가 정상 렌더되는 것은 확인. **다만 "우측에서 계산한 값이 좌측 폼 필드(판매가 등)에 실제로 반영되는지"는 아직 실제 입력 조작으로 검증 안 함.**

### 요청 사항
1. 우측 패널의 "권장 판매가"(스크린샷 기준 "27,300원" 같은 계산 결과)를 클릭했을 때 좌측 "판매가" 필드에 실제로 채워지는지 코드 확인 + 브라우저 실측.
2. 반영이 안 된다면(별개 계산기일 뿐 연동 안 됨) — 이건 UX 개선 기회다: "이 가격 적용" 버튼을 추가해 원클릭으로 좌측 폼에 반영되게(전 상품 공통, 반복 작업 감소).

### write set
`src/app/products/new/page.tsx`(마진 계산기 섹션) — 확인 후 필요시 소규모 수정.

## #4. 우측 패널 UX 개선 (즉시할인 위치 등)

### 운영자 신고
"오른쪽 실전마진계산기의 즉시할인 단위가 아래 한칸에 있어서 UI/UX 구조가 불편합니다."

### Desktop 스크린샷 확인
현재 레이아웃: 도매가(공급가) / 판매가 두 입력 칸 → 그 아래 별도 줄에 즉시할인(원/% 토글 + 숫자입력) → 그 아래 실계산 결과. **판매가와 즉시할인이 시각적으로 분리**돼 있어 판매가 대비 할인이라는 관계가 한눈에 안 들어옴.

### 개선 방향 (프리미엄 B2B SaaS 원칙)
1. **판매가 입력 칸 바로 옆(또는 안)에 즉시할인 토글+입력을 인라인 배치** — "판매가 27,600원 [-] 즉시할인 [500] [원▾]" 같은 한 줄 구성으로 논리적 인접성 확보.
2. 전체 우측 패널이 "입력 → 결과 → 경쟁채널 비교 → SEO 팁"으로 섹션이 많은데, **시각적 위계(폰트 크기·색 대비)를 더 명확히** — 가장 중요한 숫자(순마진율)가 이미 크게 보이는 건 좋으나, 나머지 카드들과 구분이 아직 약함.
3. 이건 디자인 판단이 필요한 작업이라 Code가 구체적 mockup보다는 **최소 변경(인라인 배치)** 위주로 먼저 개선하고, 결과물을 Desktop이 브라우저로 확인 후 추가 다듬기.

### write set
`src/app/products/new/page.tsx`(마진 계산기 섹션, #3과 같은 영역이라 함께 작업 가능) 또는 `src/components/products/MarginCalculator.tsx`.
