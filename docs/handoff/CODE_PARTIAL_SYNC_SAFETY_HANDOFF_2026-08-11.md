## 1. 발견된 위험 (운영자가 실제 발견, Desktop이 근본원인까지 확정)

부분재연동 실전 투입 대상으로 "듀얼 무선 가습기"(`cmsk2387l0001vzjevn46oxa4`)를 골라 dryRun 모달을 열었더니, **미리보기에 "카테고리코드: -"(빈 값)**로 나왔다. 그런데 **운영자가 클로드 크롬으로 실제 네이버 판매자센터를 확인한 결과, 이 상품의 카테고리는 "디지털/가전>계절가전>가습기>초음파식가습기"로 정확히 설정돼 있었다.**

**만약 이 상태로 confirm:true를 실행했다면, 네이버 v2 PUT은 FULL REPLACE라 앱 DB의 빈 카테고리 값이 그대로 전송되어 실제 네이버의 정상 카테고리를 지웠을 것이다.** Desktop이 이 위험을 감지해 실행을 중단했다.

## 2. 근본원인 확정 (Desktop 조사)

**규모 확인(DB 실측, 발행된 6개 상품 전체)**:
```
naverCategoryCode 빈 값: 5/6건(83%)
```

즉 **현재 발행된 상품 대부분이 앱 DB에는 카테고리·원산지 정보가 없는데 네이버에는 정확히 설정돼 있는 상태**다.

## 3. 근본 수정 방향 (전 상품 공통, 최우선)

부분재연동(dirty-field 감지 + dryRun 프리뷰 + confirm 실행) 자체의 로직은 정확하다 — 문제는 **"기준선(hydrate 시점 값)"이 애초에 신뢰할 수 없다**는 것. 앱 DB 필드가 비어있다고 해서 "이 필드는 원래 비어있었다"고 가정하면 안 된다.

### 옵션 A(권장) — confirm 실행 직전 GET으로 실제 네이버 값을 먼저 확인·병합
현재 `/api/naver/products/update`가 이미 "GET 방어 병합"을 구현하고 있다고 알려져 있음(설계 문서 §3-C 확인 필요 — Code가 이전에 "기존 쓰기 파이프라인에 GET-merge 방어가 이미 있다"고 보고한 바 있음). **이 GET-merge 로직이 정확히 이 상황을 막아주는지 재확인**:
- 만약 GET-merge가 "앱이 안 보내는 필드는 네이버 값 유지"까지 커버한다면 — 문제는 dirty-field 계산이 **빈 문자열도 "값이 있다"고 보내버리는 것**일 수 있음. 빈 문자열/null인 필드는 payload에서 아예 제외하고 GET-merge가 기존 네이버 값을 유지하게 해야 함.
- 만약 GET-merge가 없거나 불완전하다면 — 반드시 추가.

### 옵션 B — 앱 DB 자체를 정확한 값으로 먼저 보정(백필)
1회성 스크립트로, 발행된(`naverProductId` 있는) 상품들의 실제 네이버 값(카테고리·원산지·이미지 등)을 GET으로 조회해 앱 DB를 채운다. 다만 이건 "임시 보정"일 뿐 — 근본적으로는 옵션 A(빈 값은 절대 PUT 안 하는 것)가 항상 같이 있어야 한다(향후 다른 이유로 앱 DB에 공백이 생겨도 안전하도록).

### 필수 — 두 옵션 다 진행 권장
1. **즉시(옵션 A)**: dirty-field 계산이나 payload 구성 단계에서, **값이 비어있는(null/빈문자열) 필드는 "변경됨"으로 취급하지 않고 payload에서 제외**하도록 방어 로직 추가. 이게 근본적인 안전장치.
2. **후속(옵션 B)**: 발행된 6개 상품(전부 원산지 null, 5개 카테고리 빈값)을 대상으로 네이버 GET을 호출해 앱 DB를 실제 값으로 보정하는 일회성 작업. 이건 **원산지/카테고리 뿐 아니라 다른 필드도 같은 문제가 있을 수 있으니, 전체 필드(product-builder.ts 18개 화이트리스트 전부)를 대상으로 점검**.

## 4. 검증 방법
1. 옵션 A 구현 후, "듀얼 무선 가습기"로 다시 dryRun 모달을 열어 **카테고리코드가 빈 값이 아니라 실제 네이버 값(또는 최소한 "변경 없음, 기존 유지"로 명확히 표시)**으로 나오는지 확인.
2. 의도적으로 빈 필드가 있는 다른 상품으로도 같은 테스트해서 일관되게 안전한지 확인.
3. **실제 confirm:true 실행은 이 안전장치가 확실히 검증된 뒤에만.** 이번에도 아직 실행하지 말 것.
