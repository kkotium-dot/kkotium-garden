## A. #1 카테고리 오분류 — 강제 폴백은 해소, 잔여 오분류 존재

Desktop이 신선한(캐시 미적중) 상품명으로 재현:
```
"반려동물 자동급식기 스마트" → 가구/인테리어 > 주방가구 > 그릇장/컵보드  (여전히 무관)
"캠핑용 접이식 랜턴 후레쉬"   → NONE (빈 배열, 정직한 실패)
"USB 미니 선풍기 손선풍기"   → NONE (빈 배열, 정직한 실패)
```

**진단**: 강제 폴백 제거(8541d04)로 대량 쏠림은 해소됐다(이전엔 100% 가구/인테리어, 지금은 다양). 하지만 AI(Groq)가 "반려동물 자동급식기"를 여전히 "가구/인테리어"로 잘못 답하는 개별 사례가 남아있다 — 이건 강제 폴백과 무관한, AI 모델 자체의 오분류(주방가구 쪽 오답)로 보인다.

**요청**: `validateSuggestion()`의 fuzzy 매칭 단계(특히 3번 케이스 — d1 exact, d2 char-overlap 50%만으로 매칭)가 이런 개별 오답을 통과시키고 있는지 점검. 필요시 신뢰도 임계값을 높이거나(현재 스코어 기준 재검토), 반려동물 관련 상품이 "반려동물" d1으로 가야 한다는 도메인 힌트를 프롬프트에 추가하는 것도 검토(단, #1 원래 버그처럼 과도한 하드코딩 지시는 피할 것 — 화이트리스트가 아니라 "이런 키워드는 이 d1일 가능성이 높다"는 참고용 힌트 수준으로).

## B. dome_category_cache 오염 캐시 정리

Code가 결과문서에 남긴 미결 사항. `getCachedMapping`이 프롬프트 수정 이전에 저장된 "가구/인테리어" 오답을 계속 서빙할 수 있음.

**요청**: 
1. `dome_category_cache` 테이블에서 `d1='가구/인테리어'`인 레코드 중 `confidence`가 낮거나(60 이하, fallback 소스) 의심스러운 것들의 개수·샘플을 먼저 조회해 규모 파악.
2. 규모가 크면 **전체 삭제보다 "재검증 후 폐기" 전략** 검토(예: 캐시에 `createdAt`이 있다면 프롬프트 수정 커밋 시각 이전 것만 선별 삭제).
3. DB 변경은 신중히 — 삭제 범위를 정확히 확인 후 운영자 확인 없이 진행 가능한 규모(예: 명백히 소수)면 진행, 애매하면 Desktop/운영자에게 규모를 보고하고 확인 요청.

## C. #5+6 씨앗심기 프리필 — end-to-end 미검증 (Code가 검증 필요)
