## #1 — 씨앗심기 카테고리 추천 "가구/인테리어" 대량 오분류 (최우선)

**수정**: `src/app/api/category/suggest/route.ts`의 `suggestWithGroq()` 프롬프트에서
```
- For unknown items: use 가구/인테리어 > DIY자재/용품 > 기타DIY자재/용품
```
줄을 완전히 삭제하고
```
- If the product does not clearly match any category you know, respond with an empty array [] instead of guessing.
```
로 교체. `suggestFallback()`의 `FALLBACK_RULES`는 전수 확인 결과 와일드카드 캐치올 규칙이 없어(모든 규칙이 구체적 키워드 매칭) 추가 수정 불필요 — 매칭 없으면 자연스럽게 빈 배열 반환.

**검증**:
- 신규(캐시 없는) 상품명 3건으로 재현 테스트 → 더 이상 100% "가구/인테리어"로 쏠리지 않음. 한 건은 AI가 스스로 빈 배열을 반환해 `suggestFallback`으로 자연 이관됨(설계대로 동작).
- 클라이언트(`products/new/page.tsx`)는 `suggestions.length === 0`을 이미 안전하게 처리(자동채움 시도 안 함, 크래시 없음) — 별도 수정 불필요.

**⚠️ 잔여 이슈 (운영자 확인 필요)**:
1. **캐시 오염**: `dome_category_cache`(name_hash/dome_code)에 수정 전 프롬프트로 저장된 "가구/인테리어" 오답 매핑이 남아있음. 캐시 조회가 AI 호출보다 먼저 실행되므로(`route.ts` 최상단), 이미 스캔된 적 있는 상품명은 프롬프트 수정과 무관하게 계속 캐시된 오답을 서빙함. **DB에서 `d1='가구/인테리어'`인 캐시 행을 얼마나 지울지는 운영자 판단이 필요**(전체 삭제 시 재계산 비용 발생, 부분 삭제 시 기준 필요) — 이번 작업 범위에서 DB는 건드리지 않음.
2. **AI 자체 정확도 한계**: 강제 지시를 지웠어도 Groq가 스스로 "가구/인테리어"를 답할 수는 있음(테스트 중 1건 확인 — "무선 반려동물 자동급식기"). 이는 결정론적 강제 폴백이 아니라 모델 자체 판단이라 100% 제거는 불가 — 이번 수정의 목표(전수 강제 쏠림 제거)는 달성됐고, 잔여 오분류는 `validateSuggestion()`의 fuzzy 매칭 기준 재검토(핸드오프 §1-5)로 이어서 개선 가능.

## #2 — 네이버 상품번호로 상품 가져오기 작동 안 함

**근본 원인 확정**: 서버(`/api/products/import`)는 정상 동작(성공/스킵/실패를 항목별로 정확히 반환)했으나, 클라이언트(`NaverImportModal`의 `doImport()`, `src/app/products/page.tsx`)가 **응답 body를 전혀 읽지 않고** 무조건 성공 취급 → 모달을 닫고 새로고침만 했음. 실패해도, 전부 스킵돼도 사용자에게 아무 신호가 없어 "작동 안 함"으로 체감됨.

**수정**:
- `doImport()`가 응답 JSON을 파싱해 `imported`/`skipped`/`failed` 개수를 확인, 실패가 있으면 첫 번째 실패 사유를 포함한 에러 메시지 표시, 스킵만 있으면 "이미 연동된 상품입니다" 표시.
- 전체 선택 가져오기 버튼은 **완전 성공했을 때만** 모달을 닫도록 변경(부분 실패 시 에러를 보여준 채 모달 유지).
- 상품번호 직접 입력도 성공 시에만 입력창을 비움(실패 시 재시도하기 쉽도록 값 유지).

**검증**: 브라우저에서 존재하지 않는 상품번호(`999999999999`)로 실측 → `0개 연동 완료 · 1개 실패 (999999999999: Naver API GET /v2/products/origin-products/999999999999 실패: HTTP 404)` 정확히 표시됨. 수정 전에는 아무 메시지 없이 모달만 닫혔음.

## #4 — 마진 계산이 스토어 즉시할인 적용가를 제외

**근본 원인 확정**: 앱 전체 마진 분석(`/api/profitability`)은 `effectivePrice = salePrice - instant_discount`(원화)로 계산하는데, `/api/products/import`가 상품 생성 시 `instant_discount`를 전혀 채우지 않았음(항상 `null`→0). 네이버 원상품 상세에는 `customerBenefit.immediateDiscountPolicy.discountMethod`(PC 우선, PERCENT/WON)에 즉시할인 정보가 있음 — 이걸 안 읽었던 것.

**검증**: 코드 레벨 확인(실제 할인 걸린 네이버 상품으로 재현 테스트는 승인된 테스트 상품이 없어 미실시 — 필드 매핑은 Naver 공식 Discussion #241의 스키마로 확인). `/api/profitability`가 이미 이 필드를 소비하므로 배관만 연결하면 즉시 반영됨.

## A — 카테고리 잔여 오분류 ("반려동물 자동급식기" → 가구/인테리어>주방가구)

**진단 방법**: `suggestWithGroq()` 호출 직후 raw AI 응답과 `validateSuggestion()` 입출력을 임시 로그로 찍어 재현(작업 후 제거) — Desktop이 의심한 fuzzy 매칭 단계가 아니라 **AI가 문자 그대로 이미 DB에 존재하는 완전한 실제 카테고리("가구/인테리어 > 주방가구 > 그릇장/컵보드")를 답하고 있었다**(fuzzy 보정 없이 1번 exact-match 분기로 바로 통과). fuzzy 매칭 자체는 무죄.

**진짜 원인 2가지**:
1. **AI 자체 오분류**: "그릇장/컵보드"(주방 식기장 가구)와 "급식기"(먹이통) 사이 어휘적 유사성("그릇")으로 인한 모델 착오로 추정.
2. **`FALLBACK_RULES`의 반려동물 규칙이 애초에 존재하지 않는 카테고리 축을 가리키고 있었음**: 기존 규칙이 `d1: '반려동물', d2: '강아지'/'고양이', d3: '사료'`였는데, 실제 DB 축은 `d1: '생활/건강' > d2: '반려동물' > d3: '강아지 사료'/'고양이 사료'`다(`naver-categories-full.ts` 확인). "반려동물"은 d1이 아니라 d2다. 그 결과 AI가 실패해도 안전망(fallback)이 매번 `selfValidateSuggestions()`에서 드롭돼 **반려동물 상품은 폴백조차 못 받고 있었다**(강아지/고양이 키워드가 있어도 빈 배열).

**수정** (`src/app/api/category/suggest/route.ts`):
1. `FALLBACK_RULES`의 강아지/고양이 규칙을 실제 DB 축(`생활/건강 > 반려동물 > 강아지 사료`/`고양이 사료`)으로 정정.
2. 급식기/급수기 신규 규칙 추가(`생활/건강 > 반려동물 > 식기/급수기`, 실제 leaf `자동급식기`가 이 아래 존재함을 DB로 확인).
3. AI 프롬프트에 참고용 힌트 1줄 추가: "반려동물/펫 관련 용품 → d1은 '반려동물'/'펫용품'이 아니라 '생활/건강' > '반려동물' > (구체적 하위카테고리)" — 강제 정답 지시가 아니라 축 정정 힌트(#1 원래 버그처럼 하드코딩 폴백을 만들지 않도록 followup 지시 그대로 따름).

**검증(로컬 curl, 신선한 상품명 5개 재현)**: 수정 후 "반려동물 자동급식기"류 질의가 더 이상 "가구/인테리어"로 안 나오고 **"생활/건강 > 반려동물" 축으로 정확히 이동** 확인(정확한 leaf는 AI 응답에 따라 "강아지 간식"/"기타반려동물용품" 등으로 다소 부정확할 수 있으나, 최소한 최상위 대/중분류는 항상 맞게 됨 — 이전엔 아예 무관한 가구 카테고리였음). 기존 정상 케이스(잠옷, 강아지 사료) 회귀 없음 확인.

## B — dome_category_cache 오염 정리

**규모 파악(Supabase 프로덕션 DB 직접 조회)**: `category_mappings` 테이블 전체 32행 중 `naver_d1='가구/인테리어' AND source='ai'` 9건만 후보. 생성 시각 대조 결과:
- 7건: 프롬프트 수정 커밋(`8541d04`, 2026-08-10 02:33:16 UTC) **이전** 생성 → 옛 강제폴백 프롬프트가 만든 오답 확정.
- 2건: 수정 **이후** 생성이지만, A 조사 과정에서 Code(나)가 직접 재현 테스트로 만든 것("그릇장/컵보드" 케이스) — 실사용자 데이터 아니고 방금 만든 테스트 부산물.

같은 `d1='가구/인테리어'`라도 `source='fallback'`인 3건(인터폰박스·기타장식용품·방향제/디퓨저, 2026-05 생성)은 `FALLBACK_RULES`의 정상 규칙 매칭 결과로 이번 버그와 무관 — **건드리지 않음**.

**처리**: 규모가 9건으로 명백히 소수(followup 지시 "명백히 소수면 진행")라 판단해, 해당 9건을 id 지정 삭제(전체 삭제 아님, 정확히 이 9개 행만). 삭제 후 재조회로 0건 확인.

## C — 씨앗심기 프리필 end-to-end 브라우저 검증

**절차**: 실제 판매 중인 네이버 상품(원상품번호 `13564133057`, "명화 차량용방향제...")을 `/api/products/import`로 실제 가져오기 → DB 직접 조회로 필드 확인 → `?edit={id}`로 씨앗심기 화면을 브라우저로 열어 프리필 확인 → `/api/products/{id}` DELETE로 테스트 상품 정리.

**DB 확인**: `naverCategoryCode='50003356'`, `description` 609자 채워짐, `tags=["에어컨냄새제거","차량용디퓨저","명화"]`, `images=[]`(이 상품은 네이버에 추가 썸네일이 없어 원래 빈 배열 — 정상), `instant_discount=null`(이 상품은 즉시할인이 걸려있지 않아 정상 null).

**브라우저 확인**: `?edit=`로 열자 ① 카테고리 4단계 전부 정확히 프리필(가구/인테리어 > 인테리어소품 > 아로마/캔들용품 > 아로마방향제/디퓨저, 코드 50003356 일치) ② 판매가 29,000원 프리필 ③ 대표 썸네일 이미지 URL 프리필 ④ 검색최적화 탭 "태그 미완성 (3/10)" — DB의 태그 3개가 폼에 로드됐음을 확인(10개 만점 중 3개 존재 표시). `description`은 이 화면에 직접 편집 가능한 텍스트박스가 없어(내부적으로 AI 컨텍스트·엑셀 매핑에만 쓰임) 육안 확인은 못 했으나, 이전 세션에 `productFormHydrate()`가 `dto.description`을 정확히 읽는 것을 코드로 이미 확인했고 DB에 값이 있는 것도 확인했으므로 신뢰 가능.

**미검증 잔여**: 이 테스트 상품은 즉시할인이 0원이라 #4(할인가 반영)의 "실제 할인 있는 상품" 시나리오는 여전히 미검증. 다음에 즉시할인이 걸린 실제 네이버 상품을 가져올 기회가 있으면 `instant_discount`가 채워지는지 한 번 더 확인 권장(급하지 않음 — 코드 로직은 Naver 공식 스키마 기준으로 이미 검증됨).

**정리**: 테스트 상품 DELETE 완료(DB 재조회로 0건 확인). 이 상품의 `naverCategoryCode`(50003356)에 대한 `category_mappings` 캐시는 2026-05-18에 이미 존재하던 것으로 이번 테스트가 만든 게 아니라 그대로 둠.
